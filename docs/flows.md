# Agent flows

The loop runs distinct phases: **discovery** (build the watchlist; enrich = basic-info hunt + logo verify, no scrape) → **scan** (per-job enrich + match) → **shortlist** (rank the SCANNED survivors) → **walkthrough** (one job, one application) → **post-submission tracking**. The **opportunity flow** (recruiter outreach, referrals, applied-then-followup) is a parallel flow that opens and closes with a clean focus state.

## Discovery flow

**Layer A — candidate names.** Two paths, both conversational (there's no add-companies flow / mode picker anymore): (a) the user NAMES companies → Hank calls `create_companies` (then `enrich_companies` to look them up); (b) the user wants IDEAS → Hank **asks what kind first** ("let's add companies" says they want a round, not what's in it; a direction-less search returns names adjacent to the watchlist they already have, costing them a round to correct) and then calls [`find_companies`](../src/server/agent/tools/registry/findCompanies.ts) with their answer as `direction`, which runs the [`findCompaniesSubAgent`](../src/server/subagents/registry/findCompanies.ts) sub-agent (thesis + resume + the watchlist as signal; `web_search` + `fetch_url` available, it decides whether to search) and returns `[{name, oneLineReason, summary?, url?}]` onto the **discovery panel** — `summary` being 2-4 sentences of what the search actually established, which is the ONLY grounding the main agent has when the user asks about a candidate (it has no web tools, so without it an elaboration is parametric recall it can't label as such), every row pre-checked (errors when there's no thesis AND no direction — the tool then asks the user what they're after). **An empty result never renders an empty panel:** `findCompaniesSubAgent` can return `ok:true` with zero candidates (all already on the watchlist); the tool opens no panel and hands Hank a note so it narrates "nothing new" and offers another angle — no dead-end. **Re-steering is Hank's call and only Hank's**: the panel has no search-again control, so a user pushing back on a batch ("these are all too big", "more like Ramp") reaches the search only if he recognizes it as a re-run rather than a commit and calls `find_companies` again with what they said as `direction`. Both the tool description and the watchlist prompt body spell that case out; it's the one place this design depends on routing rather than a button. **Hank negotiates on the panel, not just about it**: `update_discovery_proposal` moves one company's mark, and naming a company that isn't on the list is how it joins — the same dual role `update_shortlist_proposal` has on the board, so "drop H" and "add Ramp too" are one tool. `find_companies` REPLACES the list by default and appends only when asked (`append`), because a fresh look is normally a fresh batch. **An unexplained uncheck is a question, not a commit**: when the user drops a candidate and says nothing about why, Hank asks once for the whole batch before committing — the dropped name is the most transferable correction they can give, and it transfers only as a reason. The same rule now runs on the shortlist board's relay. **Getting back to the panel is routing too**: the list hangs off no entity and sits in no menu, so the announcement line carries a `<focus-ref refKind="discovery"/>` chip (the id-less variant — a user has exactly one open list) that re-opens it, and `show_discovery` covers the same thing asked in words.

**The panel owns the BITS; chat owns the reasons.** Every candidate is written to `CompanySuggestion` when the search runs and settled when Hank commits ([`companySuggestions.ts`](../src/server/entities/companies/companySuggestions.ts) + [`suggestionMark.ts`](../src/server/entities/companies/suggestionMark.ts) → [`runCommitDiscovery`](../src/server/procedures/registry/commitDiscovery.ts)). It is deliberately NOT a `Company`: a stub per passed-on name would fill the watchlist, dashboard, and what's-next with things the user said no to sight-unseen. **A pass carries the name and nothing else** — no reason code, no per-row note. Which names are wrong is tedious to type and worth a click; *why* is one sentence that covers the whole batch and reaches the search as `direction` plus memory via the consolidation pass.

**Every row arrives CHECKED, and `userMark` is the override where null means "I accept the proposal".** Surfacing a company IS the proposal that it's worth tracking, so agreeing costs no clicks and the work is unchecking. The live mark is `userMark ?? ADD` ([`liveMark`](../src/server/entities/companies/suggestionMark.ts)) — never a raw column read — which is what makes re-checking a row a true revert rather than a second state, exactly as the board's `userVerdict` does.

**Marks relay; they do not commit.** A click writes `userMark` and nothing else — no URL hunt, no scrape, no LLM. Its divergence from `relayedMark` (compared through `liveMark` on both sides) makes it *pending*, the composer shows the count, and [`buildPanelEditBlocks`](../src/server/widgets/panelEditRelay.ts) snapshots it onto the next user message. **Hank holds the commit switch**: `commit_discovery` is `handoff: true` — the second handoff that also writes, for the same reason `commit_shortlist` is. That split is what lets the user uncheck two companies and type "and skip anything under 50 people" in one message and have both halves land.

**The commit settles the whole batch.** Checked → `ADDED`, unchecked → `DECLINED`. There is no third state to leave behind, so the panel is empty afterwards and the right panel drops back to the dashboard — the same move the shortlist board makes on commit.


**The panel shows ONE RUN — the last search's output, nothing else.** [`loadDiscoveryList`](../src/server/views/discoveryList.ts) keys on the newest open row's `runId`. Older unsettled candidates (a list the user walked away from without committing) stay in the table as *input* to the next search and are never drawn: showing them puts names on screen from a batch the user has forgotten, and makes the arm's "found you N companies" line disagree with what they can count — which is exactly the bug that shipped. A carried-forward name is re-recorded under the current run when the search re-proposes it, so it appears on its own merits rather than as a leftover.


**Suppression is ADVICE, not a filter.** `listSuggestionHistory` hands the search what was declined; nothing filters its output afterwards. That's what makes the override free — `direction` is what Hank forwards from chat, so "actually I'd look at bigger companies now" lands in the same prompt as the names previously turned down and the model reconciles them. There is no un-decline tool and shouldn't be. One hard rule survives: a name declined in the round that just happened is never re-proposed (`inLatestRound`). The fade is the model's judgment — history carries `timesDeclined` + `lastDecidedAt`, and the prompt says recent and repeated declines are strong while a lone old one is weak. The prompt also keeps the two apart deliberately: a decline names ONE company, the direction describes the SHAPE, so the model generalizes from what the user said rather than reconstructing a motive from the names.

**`nameKey` is the identity** — `slugify` of the name minus any trailing `(Division)` qualifier, since the search likes to emit "The Trade Desk (Client Partnerships)" and without stripping one company keeps two histories. Corporate-suffix variants ("Evertune AI" vs "Evertune") deliberately do NOT merge: folding those would join genuinely different companies ("Scale" / "Scale AI"), and a wrong merge suppresses something the user never declined — worse than a wrong split, which only costs a repeat question.

**A finished add asks the local question, and its primary action is LEAVING.** Once the ✓ lines land, [`addMoreCompaniesWidget`](../src/server/procedures/registry/enrichCompanies/addMoreCompaniesWidget.ts) puts up `add_more_companies` — **"Done adding"** is the primary (falls through to the what's-next picker), "Find more" the secondary (re-enters discovery with no direction, since the watchlist just grew and a fresh run reads differently). A card whose main button is "Add more" invites staying in add-mode indefinitely, which is the opposite of what finishing means. "Done adding" also runs [`runWrapSegment`](../src/server/procedures/registry/wrapSegment.ts) with `subject: "discovery"` when the round settled anything — it is a topic boundary exactly as the end of a company is, so it consolidates memory and compacts the transcript. A round that decided nothing skips it (the wrap costs two LLM calls). Both paths that finish an add emit it: the discovery commit and the disambiguation tail. It is suppressed while a disambiguation picker is still unanswered, so two widgets never stack. The full what's-next picker is the wrong thing to show a user mid-hunt — it answers a question they didn't ask — which is why the local question exists instead of falling straight through.

**Layer B — the enrich batch.** Picked/named companies → `create_companies` stubs → enrich. Both the discovery commit ([`runChecklistAdd`](../src/server/procedures/registry/enrichCompanies/runChecklistAdd.ts)) and the `enrich_companies` tool route through one shared bounded-batch primitive (no per-company loop).

**Enrichment is IDENTITY only — it does not scrape.** It answers "who is this company": canonical name, one-line description, careers/ATS URL, verified logo. Open roles are pulled in later, by the walkthrough on entry or an explicit `scrape_jobs_for_company`. So an added company lands at `NEW` with no roles, and `whats_next`'s backlog is what surfaces it (`loadBacklog` loads `READY` then `NEW`). Folding the scrape in here is what made five near-identical enrich paths drift apart.

- **Create** — [`createCompanyStubs`](../src/server/entities/companies/createCompanyStubs.ts): `Company` (`sourceUrl: null`) + `CompanyInteraction(NEW)` in one transaction, deduped by slug (existing names come back `existed`).
- **Enrich** — [`runEnrichCompanies`](../src/server/procedures/registry/enrichCompanies/enrichCompanies.ts): async generator over the stubs, bounded worker pool (`CONCURRENCY=5`; no hard cap on batch size — the "keep it to ~20 at a time" nudge is advisory and lives in Hank's prompt). Per company ([`enrichOne`](../src/server/procedures/registry/enrichCompanies/enrichOne.ts)):
  1. Stamp `huntingStartedAt` (UI "Scanning…" badge) for the whole chain, clear in a `finally`.
  2. **Basic-info hunter** ([companyBasicInfoSubAgent](../src/server/subagents/registry/companyBasicInfo.ts), judgement-class), gated on `basicInfoHuntedAt` — cascade `probe_ats` (free, deterministic) → web_search the ATS → grep homepage; a discovery `candidateUrl` is `test_scrape`d first; custom-domain ATSes (Workday, iCIMS) are resolved by running `test_scrape` on the careers page itself. Success = ≥2 real jobs AND the right company. `report_basic_info` → **`found`** (`sourceUrl`+`canonicalName`+`shortDescription`), **`ambiguous`** (name maps to ≥2 companies), or **`cannot_scrape`** (incl. a sub-brand with no own board, naming the parent). See [ats-scrapers.md](ats-scrapers.md), [sub-agents.md](sub-agents.md).
  3. **Commit** — [`commitHuntedUrl`](../src/server/procedures/registry/enrichCompanies/commitHuntedUrl.ts), the one place a hunted URL lands, carrying both `@unique` guards: a canonical **slug** another company holds falls back to the current slug, and a **`sourceUrl`** another user's Company row already holds deletes the stub and re-points this user's `CompanyInteraction` at that row (protects shared rows + notes). Stamps `basicInfoHuntedAt`.
  4. **Logo verify** — gated on `logoVerifiedAt`; [`runVerifyCompanyLogo`](../src/server/procedures/registry/verifyCompanyLogo.ts) → [`applyLogoVerdict`](../src/server/procedures/registry/enrichCompanies/applyLogoVerdict.ts). Errors are swallowed and the stamp lands either way ("verified" = the check ran), so a company with no derivable logo doesn't re-check forever.

**Which outcome writes a status is the contract.** `cannot_scrape` is a finding about the company, so the chain lands **`BLOCKED`** itself (technical set-aside, revivable, excluded from scans) and preserves the stub for a manual `update_company`. `hunter_failed` (API error / timeout) and `ambiguous` write **nothing** and hand the decision back, because the right consequence depends on who's asking — see Disambiguation below.

**`force`** (`enrich_companies({companies, force: true})`) re-runs both steps regardless of the flags, for when a company's details on file look wrong. It short-circuits the gates rather than nulling the columns — the chain re-stamps them on the way through.

**`companies/{slug}.md` is append-only** — the hunter's `longNotes` appended via [`appendMemory`](../src/server/memory/store.ts) (protects user notes on re-add). Status transitions (defer/close/block/caught-up/revive) are **not** written here anymore; they land on the first-class [`CompanyEvent`](../src/server/entities/companies/logCompanyEvent.ts) timeline behind the company "Recent activity" card, which is read into the agent's focused-company context. The hunter persists nothing mid-loop — the orchestrator writes after `runSubAgent` returns.

**Disambiguation.** A bare name can collide. Defenses: each marked row threads its `{context, url}` into the hunter; `probe_ats`/`test_scrape` confirm the board is the *right* company's; an `ambiguous` outcome is collected and surfaced as one `company_disambiguation` picker at batch end, resolved by [`runDisambiguationResolution`](../src/server/procedures/registry/enrichCompanies/runChecklistAdd.ts) (which re-enters the same chain with the picked URL, skipping the hunt). Mid-walkthrough there's no picker to render, so [`runCompanyEnrichStep`](../src/server/procedures/registry/walkthrough/companyEnrichStep.ts) sets the company aside with a note naming the candidates — the one outcome whose consequence is genuinely caller-specific.

## Re-scrape flow

[`scrape_jobs_for_company({company, context?})`](../src/server/agent/tools/registry/scrapeJobsForCompany.ts) is the canonical re-scrape for a company with a `sourceUrl` — **`handoff: true`** (it explicitly hands off to the walkthrough state machine, which then scans + shortlists the new survivors — the "nothing runs unless Hank hands off" invariant, [runtime.md](runtime.md); it used to be non-handoff and relied on a post-turn re-derivation), also auto-fired on walkthrough entry when the board is stale (`lastScrapedJobsAt` null or >24h — that path is the company arm itself, already running under a handoff). Wraps [`runScrapeJobsForCompany`](../src/server/procedures/registry/scrapeJobsForCompany.ts): gate (on the watchlist / not CLOSED / has a `sourceUrl`) → [`syncCompanyBoard`](../src/server/entities/jobs/syncCompanyBoard.ts) (`scrapeUrl` + upsert + `JobInteraction(NEW)`/`SURFACED` for unseen jobs + stamp `lastScrapedJobsAt` on success) → PRE_SCAN the delta → focus. `syncCompanyBoard` is the **shared scrape→persist core**: the walkthrough's on-entry board pull ([`runBoardScrape`](../src/server/procedures/registry/walkthrough/boardScrape.ts) — the one scrape path in the arm, entered both when the user has no roles on file and when the board is stale) runs the same core, then prescans + scans in its own Step 1. **Closure (same upsert):** jobs the board no longer returns get `Job.closedAt` + non-terminal interactions → `DELISTED` ([`detectAndApplyClosures`](../src/server/entities/jobs/upsertScrapedJobs.ts)), plus one collapsed `JOBS_CLOSED` company event; skipped outright when the scrape reported `truncatedAt`, and guarded against mass-close (bails on empty scrape or >34% drop). Delta 0 → bail; else PRE_SCAN the delta only, then the procedure itself lands the status via `markCompanyPostFilter`: `CAUGHT_UP → READY` when survivors remain, back to `CAUGHT_UP` when the whole delta skipped (`APPLYING` stays — the helper only overwrites the pre-walkthrough set).

`scrape_jobs_for_company` re-scrapes one company's live board, diffs against postings already on file, runs the cheap first-pass filter on the new ones, and (in a walkthrough) flows survivors straight into read-and-shortlist. **Don't loop it over the watchlist.** To re-check a `BLOCKED` company (careers page wouldn't read), `company_walkthrough` on it surfaces a revive confirmation and re-checks the board fresh — one at a time; there's no batch retry. [`update_company_interaction`](../src/server/agent/tools/registry/updateCompanyInteraction.ts) is a pure status/reason correction on the watchlist row — no activity-feed entry, no revive, no re-scan, and it doesn't touch the company's roles.

**Empty-result diagnostics.** A 0-job scrape attaches `{provider, fetchedUrl, pageLength, pageSnippet}`; the system prompt's rubric triages (real-empty board → CAUGHT_UP intact; fetch error/stale URL → `update_company`). Non-ATS URLs error before diagnostics. `scrape_jobs_for_company` emits a `## Expectations` block when a known-ATS host returns zero (dedupKey `scrape_jobs_for_company:zero_jobs:<provider>`). Legit same-title multi-region duplicates and short rawContent look like bugs but aren't — read the "don't delete these" comment above `upsertScrapedJobs` before writing junk-detection. See [tools.md](tools.md).

## Manual job entry (no scrape)

[`create_jobs`](../src/server/agent/tools/registry/createJobs.ts) is the manual batched path (`jobs: [{title, ...}]`, one transaction) for jobs that exist in chat without careers-page rows (referrals, email postings, logging historical applications). Only `title` is required; `company` falls back to focus. `Job.sourceUrl`/`rawContent` are nullable and consumers tolerate null (job-detail hides the posting button, `view_application_questions` returns a manual-entry hint). `sourceUrl` is `@unique` (multiple NULLs are distinct); a non-null URL collision rolls back the batch and points to [`update_job`](../src/server/agent/tools/registry/updateJob.ts) (per-field partial update). Neither touches `JobInteraction` — status goes through `log_job_events` / `close_job` / `defer_job` / `mark_job_applied`.

## Pre-scan (metadata filter)

PRE_SCAN ([`runPreScan`](../src/server/procedures/registry/preScan/index.ts), fanning out `preScanJobBatchSubAgent`) is the cheap obvious-no filter over `NEW` postings — metadata only, never bodies, parallel chunks. It runs in the **walkthrough** (step 1, over the whole not-yet-reviewed pool) and in **`scrape_jobs_for_company`** (over the delta). It does **not** run at add time: enrichment doesn't scrape, so there are no postings to filter yet.

Leans keep. Skips on location only for an explicit user-named hard-skip location (a scraped city is HQ, not remote-eligibility); role-type and off-thesis skips fire regardless. Each chunk's cached prefix carries the company's own context — `Company.description` + `companies/{slug}.md` when they exist — so the domain skip reads what the business IS rather than inferring it from the name; with neither, the prompt tells it the domain is unknown and to keep.

**Emits per-job verdicts only** — it closes the skipped roles and reports the survivors, and writes **no company status** (the sub-agent isn't even told it's one chunk of a board). The caller lands the status: `scrape_jobs_for_company` calls [`markCompanyPostFilter`](../src/server/entities/companies/markCompanyStatus.ts) (survivors → `READY`, none → `CAUGHT_UP`); mid-walkthrough only `markCompanyReady` fires, because the walkthrough's own step-3 wrap owns the ending. **PRE_SCAN can no longer `CLOSE` a company** — a metadata pass is the weakest evidence in the system, so an off-thesis domain surfaces as N `not_a_match` job skips. Nothing in the scan/shortlist chain closes a COMPANY. Every survivor stays `NEW` for the scan step.

**Cold-start bail.** PRE_SCAN returns `mode: "cold_start"` when `profile.md` is empty — nothing closed, and the callers skip their status write on that mode, so the company stays `NEW` and the next message routes into enrich-profile via `runWhatsNext` rung 0.

## Scan step

After PRE_SCAN, the walkthrough company arm runs the **scan step** ([`runScan`](../src/server/procedures/registry/scan/runScan.ts)) over the NEW survivors — where bodies get read. Two per-job passes, fanned out at `CONCURRENCY=16` (also the in-flight Anthropic ceiling):
1. **Enrich** ([`enrichJobSubAgent`](../src/server/subagents/registry/enrichJob.ts), user-independent) — reads body + raw attributes, writes `Job.enrichedSummary` (terse lossless prose) + `Job.enrichedAttributes`. **Cached on the global `Job`**, reused across users. Makes `locationAndArrangement` arrangement-aware (place + remote/hybrid/on-site) — the one column it overwrites, so an on-site role doesn't read as possibly-remote.
2. **Match** ([`scanJobSubAgent`](../src/server/subagents/registry/scanJob.ts), per-user) — reads the enriched summary + both attribute bags + thesis/resume, plus the descriptive company context (`Company.description`, `companies/{slug}.md`, and `jobs/{slug}.md` on the rare role that already has a note) that the off-thesis-domain gate reads. It gets **no** past-decision history and no session steer (the dead `extraContext` param was dropped 2026-07-28 — nothing had passed one since the walkthrough took over the call). Makes an ABSOLUTE call: `skip` → CLOSED (`NOT_A_MATCH`/`LOCATION_MISMATCH`/`OTHER`); `match` → SCANNED + `matchBucket` (STRONG/POSSIBLE/WEAK). It does NOT rank. **Skip conditions (geo, below-floor comp, role-type, seniority) are HARD GATES before bucketing — a disqualifier is a `skip`, never a demoted bucket.**

**Narration.** Scan sub-agents run without `parentToolUseId` (traces render nowhere); the user sees only the arm's narration: `Doing a first pass over N…` → `Reading M in full…` → `Read M — X look like a fit…`. Keep in sync if you change scan structure ([companyArm.ts](../src/server/procedures/registry/walkthrough/companyArm.ts)). **Resilience:** `runScan` aborts on 429/529 and returns `rateLimited` (resumption is free — enrichment cached, match only touches NEW); a per-job error is non-fatal (a final sweep promotes leftover NEW → SCANNED). There is no cap on how many reach the shortlist — the ranker reads every survivor in one pass.

## Shortlisting flow — the board

Shortlisting is a **negotiation over the shortlist board** — a persistent right-panel screen showing every role considered at the company, tiered, each row carrying the deciding pass's one-line reason. The negotiation state is split by WHO holds it, so neither side can erase the other: `agentVerdict`/`agentReason` are Hank's proposal and only he writes them, `userVerdict` is the override, and **`userVerdict IS NULL` means "I accept his"**. The live stance is `userVerdict ?? agentVerdict` ([`liveVerdict`](../src/server/entities/jobs/boardStance.ts)); "a negotiation is open" is the derived predicate *any row has a stance or a placement*. Statuses change only at commit.

That split is what makes re-marking a row back onto Hank's proposal restore his reason — [`setBoardStance`](../src/server/entities/jobs/setBoardStance.ts) stores it as `null` rather than a duplicate of his verdict, so the disagreement ends instead of persisting as a matching-but-overridden pair. Same revert-is-a-no-op property the application page gets from `proposedDrafts`.

**A row shows ONE reason**, the stance reason. The scan pass's earlier read surfaces only when it *contradicts* the stance — two steps apart on the axis (`STRONG`↔pass, `WEAK`↔pick); `POSSIBLE` contradicts nothing and a one-step gap is ordinary re-ranking. Hank's own verdict is labelled on a row only where the user overruled it; on an untouched row his reason IS the row's reason.

**Nothing is closed until the round is committed.** The metadata pass and the full read do not close a role — they write a `PASS` stance carrying their reason ([`passOnJobs`](../src/server/entities/jobs/passOnJobs.ts)) and leave the status alone, so a role they rule out is an ordinary board row with Close pre-selected. Marking it Shortlist or Defer is just changing a mark; there is no un-close, no revive, and no read-only tail. `commit_shortlist` is the ONLY thing in the system that closes a role.

That also removes every timestamp comparison the round used to need: **a cleared stance IS the round boundary**. A commit clears them all, so "carries a stance" means "in the round in progress" — which is why the shortlist pool skips already-stanced rows (the ranker never re-litigates a call the user can already see) and why the walkthrough can gate its shortlist rung on `openStanceCount` alone.

**One rung, one entry point.** [`runShortlist`](../src/server/procedures/registry/shortlist/runShortlist.ts) is the walkthrough company arm's Step 2, reached when SCANNED roles await a seed, a negotiation is open, or a `direction` asks for a fresh ranking. Three branches fall out of state — no gates, no persisted step pointer:
- **Open negotiation, no `direction`** → re-show the board where it stands (free — no LLM, so no re-emit guard either).
- **`direction`** ("infra roles only") → fresh seed on those terms; the pool includes committed picks + passovers, so they get re-weighed too.
- **Otherwise** → seed the pool.

**The seed** — [`loadShortlistJobsInput`](../src/server/procedures/registry/shortlist/loadShortlistJobsInput.ts) assembles the pool + candidate context (scan verdicts, what the company does, `profile.md`, the resume summary, `companies/{slug}.md`, per-role `jobs/{slug}.md` notes, and on a re-rank the `deferNote` from the last commit), hands it to [`shortlistJobsSubAgent`](../src/server/subagents/registry/shortlistJobs.ts) — a rollup sub-agent with **no tools and one turn** — and gets one `{reason, stance}` per candidate: `pick` / `borderline` / `pass`. [`seedBoardStances`](../src/server/procedures/registry/shortlist/seedBoardStances.ts) applies the pick ceiling (`SHORTLIST_CAP=5`, demoting extras to borderline) and lands the stances in one transaction — **no status changes, no closes**. Then the board goes on screen and a deterministic line invites the discussion. **Selectivity:** the 3-5 strongest, not a quota (a small pool picks all genuine fits).

**The negotiation.** The board shows roles still being considered — status `NEW` / `SCANNED` / `SHORTLISTED` / `APPLYING` / `DEFERRED` (`CONSIDERED_STATUSES`) — **plus this round's automatic closes**, so the filtering stays auditable while the round is open. Roles decided in an EARLIER round are off it entirely: the user watched them go, and the company page's never-pursued list is where they live; reopening one of those is a repair (`update_job_interaction`), not a board move.

**Every row carries the same three marks and exactly one is set** ([`StanceMarks`](../src/components/RightPanel/shared/StanceMarks.tsx), a radio group — re-clicking the set mark does nothing, because there is no no-opinion state to clear to and `borderline` already means "don't close it, don't commit to it"). Agreeing with Hank costs no clicks. That uniformity is what removed the board's one bespoke control: a role the automatic passes ruled out shows Close already set, and marking it Shortlist or Defer is just a different mark on an open row. [`runReconsiderJob`](../src/server/procedures/registry/reconsiderJob.ts) is the single path for every mark. A still-`NEW` role marked Shortlist/Defer is read first and promoted out of `NEW` (→ `runEnrichJobBody`): being in the pool is what stops the next scan pass re-triaging a role the user just picked, and the human choosing it IS the judgment, so the match pass is not re-run to argue back.

**The same marks are on the role's own page.** Opening a role from the board is how a user decides the ones the summary couldn't settle, so [`JobDetailView`](../src/components/RightPanel/JobDetailView.tsx) renders the same control (plus a back-link to the rest of the board) whenever `FocusedJobView.board` is non-null — a round is open at that company and this row can still hold a stance. Both surfaces write through `editShortlistBoard`, so a mark means the same thing from either.

**Marks don't move rows until the next message.** A row's group follows `placementVerdict`, not the live stance: the user's mark writes `proposedVerdict` alone, so the row stays where they're looking at it, flagged pending. Their next message relays the change ([`buildPanelEditBlocks`](../src/server/widgets/panelEditRelay.ts) → a `panel_edits` block) and settles placement in the same step, which is when the board re-files. Hank's own moves set both — he acts inside the conversation the user is watching — so a divergence always means "unrelayed user edit", which is also how the relay finds them (no timestamp window to race, and a mark-and-undo reports nothing). While boards are open, Hank's per-turn context carries a compact rendering ([`loadHankShortlistBoardContext`](../src/server/agent/hank/shortlistBoardContext.ts)) that names any pending mark on the row it's still grouped under.

**The commit** — Hank's `commit_shortlist`, called when the user signals agreement (handoff: the role picker follows deterministically). [`commitShortlist`](../src/server/entities/companies/commitShortlist.ts) decides every stanced row in one transaction: PICK → `SHORTLISTED` (or **stays `APPLYING`** on a role whose application is already being written — picking one of those is agreement, and writing `SHORTLISTED` over it would say "queued" about the one in progress); BORDERLINE → `DEFERRED` + `OUTRANKED` with `deferNote ← proposedReason`; PASS → `CLOSED` (`NOT_A_MATCH`, `closeNote ← proposedReason`); all stances cleared; company bumped to `APPLYING` when anything was picked (that is what APPLYING now MEANS — before the commit it is `SHORTLISTING`); ONE collapsed `SHORTLIST_RAN` company event. Stance-less rows are untouched. A row whose status moved PAST the board mid-round (applied to, answered, delisted) has its stance dropped rather than acted on — a stale `pick` must not write `SHORTLISTED` over a role the user just told Hank they'd applied to.

**Closing a role whose application was started asks first.** The commit returns `CONFIRM_CLOSING_STARTED` with the titles instead of writing, and Hank re-calls with `confirmed: true` once the user agrees — the same shape as `caught_up_company`'s open-roles bail. Everything else a commit does is reversible in a sentence; this one closes a role with work in it (the draft survives on the record, but the role leaves every pool that would surface it again). Deferring one needs no confirmation — it stays in the pool and the draft is untouched. The panel's **Looks good to me** has no way to ask, so it falls through to Hank on that refusal and he hits the same gate.

The pool predicate [`shortlistPoolStatusWhere`](../src/server/entities/jobs/shortlistPool.ts) — `SCANNED + SHORTLISTED + APPLYING + (DEFERRED where reason = OUTRANKED)` — is what keeps the round reversible: a later re-seed pulls committed passovers back in.

**`APPLYING` is in the pool on purpose: a half-written application must not be invisible to the next round.** Left out, a role the user had committed to and stopped writing was neither ranked nor on the board, so they compared this company's roles against a picture missing it. It is ranked in place and never demoted on the way in — the status changes at commit like every other row's. The ranker is told (`unfinishedApplication` → "Application started and never finished") and may land it anywhere including `pass`, but the prompt requires it to say so in the reason, and `runShortlist` names those roles in the seed message deterministically rather than trusting an LLM to remember. The board row carries the same tag, because the chat line scrolls and the commit happens on the board. If the user answers "I actually applied to that", `mark_job_applied` clears the stance and the row leaves the round.

**Close vs caught-up vs blocked.** No automatic path closes a COMPANY, and nothing closes a ROLE before commit. An *all-pass seed* opens the board with everything in the pass tier and narrates the shared reason; if the user agrees, the commit closes them, the pool empties, and the NEXT pass through the company arm hits the *metadata-cull* branch (`liveCount===0 && skippedCount>0`), which narrates what was set aside (`summarizeCloseRationales`), calls `caughtUpCompany`, and returns `wrappedUp: true` + `endedCompanyId`.

**A round that ruled EVERYTHING out still gets a board.** Where the pool empties — the metadata pass, the full read, or the ranker passing on the one survivor — is an implementation boundary the user cannot see, and it used to decide whether they got a screen at all: one company opened a board with a single passed role, the next went quiet and landed caught-up. The automatic passes stance what they rule out, so a boardful of passes exists either way and `openStanceCount` alone carries the rung. The trigger is **nothing PICKED**, not nothing kept: a round whose only survivors are holds has produced nothing to work on, and routing there means "choose one to apply to" over roles Hank recommended against. The panel shows an icon and one line, its commit pill reads **"Nothing here — mark them caught up"** rather than "Looks good to me", and the reasoning goes in chat where there's room for it. Committing needs no new status write — nothing is picked, so the walkthrough's own tail reaches the metadata-cull branch and lands `CAUGHT_UP` — and the cleared stances are what stop it re-entering the board it just settled.

**That narration reports the MIX, with counts, scoped to this round** — "12 were sales roles, 3 were product roles, and 2 were in Europe", from a plain tally of the per-job `closeSummaryLabel`s the pre-scan/scan sub-agents emit. Two rules make it honest, and both replaced a version that wasn't. It never collapses to a single dominant reason: the sentence renders as *"I went through their N open roles and none line up — {detail}"*, so naming one category there is a claim about all of them, and the minority groups are exactly the ones worth revisiting (a role that's the right job in the wrong city, versus one that was never the right job). And it counts only closes since [`roundStartedAt`](../src/server/entities/jobs/boardStance.ts), so an earlier round's dominant reason can't keep voting and the "N open roles" number can't drift past what this pass actually looked at. A round that closed nothing falls back to the generic sentence rather than claiming a number. Company `CLOSED` is reached only through `close_company`; "no fit now but could post later" is `CAUGHT_UP`; "couldn't read the board" is `BLOCKED`.

**No round-completeness gate.** A commit decides only the stanced rows: a still-NEW straggler shows on the board's "not read yet" tier and flows into the next seed once scanned. For a single-job nudge or repair, `update_job_interaction({status:'SHORTLISTED'})` still lands directly (a repair write — no timeline event, stances cleared).

**Empty-company prep keys on the *user's* JobInteractions**, not global `Job` rows — a discovery-added stub can carry another user's Jobs while this user has zero JobInteractions; gating on the user's JobInteractions makes the walkthrough's on-entry board scrape ([`runBoardScrape`](../src/server/procedures/registry/walkthrough/boardScrape.ts)) create their JobInteractions first.

**Reviving a set-aside company.** Naming a `CLOSED` or `BLOCKED` company in `company_walkthrough` emits `confirm_revive_company`; "yes" runs `reviveCompany` (reactivate + fresh re-scrape → continue), "no" → next-company picker. Revive re-hunts the board and scans only genuinely-new postings; previously-closed roles stay closed — and now stay *visible* on the board's closed tiers, reconsiderable one at a time. See [runtime.md](runtime.md).

**Manual escape-hatch** (`update_job_interaction` etc.) — for when the round errors, chat-only overrides, or after a direct `scrape_jobs_for_company`. Three-tier cost gradient (filter on the cheap fields before pulling the expensive ones):

| Step | Cost per job | Cap |
| ---- | ------------ | --- |
| `scrape_jobs_for_company` lean list (title + free ATS metadata) | Free (with the scrape) | All scanned |
| `read_job_description` (DB read of `rawContent`; auto-promotes NEW→SCANNED) | Pure DB read | ≤20/round |
| `list_job_events` (event timeline) | Cheaper DB read | Anytime |
| shortlist rung → board seed | One-txn stance write | target 3-5 picks (auto caps at 5) |
| `ensureApplicationForm` (ATS questions endpoint) | One HTTP request | Once per SHORTLISTED job |

**The diligence gate that closes the round.** [`caught_up_company`](../src/server/agent/tools/registry/caughtUpCompany.ts) does not set the status on its first call if any job is still `SCANNED` or `SHORTLISTED` — it reports the open roles and asks Hank to confirm with the user, who re-calls with `confirmed: true`. `DEFERRED` doesn't block (a resolved "outranked" hold, not open business), and neither does `NEW` — an unreviewed backlog is exactly what caught-up is *for*. (This replaced a hard `CAUGHT_UP_BLOCKING_STATUSES` error on the old `update_company_status`, which stranded the user instead of asking.) The walkthrough that follows is strictly sequential.

## Job picker between roles

Once SCANNED is drained, the company arm emits the `next_job_picker` widget (not auto-focus). Two buckets: **Shortlisted** (`SHORTLISTED`, stalest first) and **Deferred** (`DEFERRED`, stalest first; shows `deferReason`, usually `OUTRANKED`). Renders confirm-first: a single card for the top active item (`Walk through {title}`) + a "See full list" toggle (bucket caps 5 + expander); no Shortlisted → straight to the full list. Picking a job routes the state machine into that job's arm (the submission carries the `jobId`, threaded as the `entryTarget` — no focus slot); picking a Deferred one does the same in a transaction that flips `DEFERRED → SHORTLISTED` and clears defer fields ("work on this now" = revival). Both buckets empty → `caughtUpCompany` (the only auto-CAUGHT_UP path). Between jobs, `close_job`/`defer_job`/`mark_job_applied` are record-only (they change no panel — focus is ephemeral); Hank brings the picker back by re-entering the company with `company_walkthrough`. "Done with this company" → `caughtUpCompany` + wrap. See [ui.md](ui.md).

## Application drafting + usage tracking

The walkthrough opens by **surveying the form**, not drafting. [`ensureApplicationForm`](../src/server/procedures/registry/draftApplication/ensureApplicationForm.ts) runs once per shortlisted job when the job arm is entered (never during scan/shortlist — forms carry only plumbing, no fit signal). It's the shared fetch-and-cache step: the drafting procedure calls it as step 1, and Hank reaches the same path through [`view_application_questions`](../src/server/agent/tools/registry/viewApplicationQuestions.ts), which lazily fetches on first call so it can never report "no questions" for a form nobody read. (The old single `get_application_form` tool is gone — it was split into this procedure step + that tool.) Greenhouse/Lever/Ashby/Workday/Teamtailor/Gem lazy-fetch and persist on `Job.applicationQuestions` ([envelope](#applicationquestions-envelope)); bespoke/unrecognized → `{status:"unsupported"}` and the agent `fetch_url`s the page once then asks the user *"Does this application have a cover letter? Any short-answer questions?"*

**The decider owns the draft/skip/ask-user call.** [`applicationDeciderSubAgent`](../src/server/subagents/registry/applicationDecider.ts) runs once per job (cached on `JobInteraction.draftDecision`). Exactly one thing is decided before it, and it's structural — no question is pre-classified by its wording:
- `isStockFieldType` (boolean/select/phone) in [types.ts](../src/server/scrape/types.ts) — hard pre-skip by widget **type**, since a dropdown has no prose answer by construction. **File uploads are NOT here** — a file field can be a resume (skip) or "Cover Letter" (compose), judged by label.
- Everything else is the model's read of the question text. The prompt renders the **whole form in order** — pre-skipped fields included, marked `[-]`, with only the decidable ones numbered `[n]` — so a conditional stub ("If yes, please explain") is readable against the field above it, which is usually one of those pre-skipped selects. `isProseQuestion` survives only as the deterministic fallback verdict when no decision is available (malformed emission / decider error).

The decider resolves the ambiguous middle with a *direct-evidence* bar for `draft` (adjacency doesn't license inventing specifics — that's `ask_user`) and a *value* bar (a short factual field is `skip` even if the resume has it). It's a **one-shot** — the caller front-loads the role's full attribute block, the posting, the résumé, `profile.md`, `frequent_questions.md` and the company/job notes, and past work reaches it as a *catalog*: which questions already have a reusable answer, which roles have a prior cover letter, never the text. Existence is the whole verdict ("we have something to adapt" → `draft`); judging how much of that text is worth reusing is `applicationDraftingSubAgent`'s call, and it holds the deep-read tool that fetches the bodies. It recognizes a cover letter from the Greenhouse attachment flag or a "Cover Letter"-labeled question ([`isCoverLetterQuestion`](../src/server/scrape/types.ts)), and treats a catch-all "additional information/anything else" field as cover-letter-equivalent (drafts unless a dedicated cover-letter field exists). Per item: **`draft`** → `applicationDraftingSubAgent`; **`skip`** → nothing; **`ask_user`** → chat co-writing. On decider error, falls back to the deterministic `isProseQuestion` rule. All-skip → a real "nothing here I'd draft … tap I submitted ✓" message, not a false "draft ready."

**Help-first on soft holds.** A *soft* memory hold ("hold off on cover letters until I trust the flow") still drafts/asks and emits a top-level `notice` the runner surfaces once ("I saw you wanted to hold off but drafted one so you can judge it"). Only an explicit standing instruction ("I never write cover letters") is a genuine `skip`.

Everything the form asks for renders on the **application page** — a right-panel mode of its own ([ApplicationView.tsx](../src/components/RightPanel/ApplicationView.tsx) over [`loadApplicationView`](../src/server/views/application.ts)), put on screen automatically whenever a pass produces something. Undrafted items are listed too, so a question the decider skipped is one the user can still fill in.

**Two baselines, because there are two questions.** `proposedDrafts` is what Hank last WROTE — only his own writes touch it. `relayedDrafts` is what he last SAW — the panel-edit relay and submit re-stamp it. Everything falls out of comparing the live text to one or the other, and picking the wrong one is a real bug class: fused into a single column, relaying an edit made the user's words read as Hank's a message later, which is why authorship briefly needed a stamped column of its own.

| Question | Compare live text to | Used by |
| --- | --- | --- |
| Whose words are these? | `proposedDrafts` | [`authorFor`](../src/server/entities/jobs/applicationDrafts.ts) / `isUserOwned`, the page's author mark |
| Has Hank seen this yet? | `relayedDrafts` | `applicationEditsFor` → the panel-edit relay, `pendingCount` |

Authorship is therefore **derived, never stamped**, and that buys the behaviour a stamp couldn't: edit an item, change your mind, put his wording back, and it is his again — because it IS his again. Neither baseline is the `*Reuse` flag, which answers "may we draw on this later".

Divergence from `relayedDrafts` IS the unrelayed-edit signal — the same proposal-vs-what's-drawn test the shortlist board runs, so no dirty flag exists and editing back to what he's seen is a no-op. In either baseline an entry with text means he wrote/saw that text, an explicit `null` means he's seen it empty, and no entry at all means no baseline.

Every write of application text goes through [`persistApplicationAnswer`](../src/server/entities/jobs/applicationQuestions.ts) — the drafting procedure, critic revisions, `draft_application_question`, `save_application_answer` — which takes an `author` and derives its side-effects from it. Hank's own writing moves BOTH baselines (he wrote it, so he's also seen it) and clears the reuse flag. The user's dictated words (`save_application_answer`, which transcribes and never composes) move only the seen baseline, so the page attributes the text to them — and touch the reuse flag not at all: **that switch auto-flips only from gestures made on the page where it's visible** (editing an item, pressing Copy, the switch itself). Flipping it from a chat message would be a change nobody could watch happen. The critic reviews the whole form but only revises what `isUserOwned` says is still Hank's; a critique of the user's own text surfaces in `unresolvedIssues` rather than rewriting their sentences. **Submit is the learning moment**: [`runCommitApplication`](../src/server/procedures/registry/commitApplication.ts) diffs what was sent against what Hank wrote, and hands the consolidation pass BOTH halves — the diff (voice, and the claims they won't make) and every answer that went out, verbatim. The second half is what `frequent_questions.md` promotion needs: a question asked in these words and answered in these words is the unit another form can reuse, and a diff of it isn't. So it runs on every submit that sent something, not only an edited one — an application that went out exactly as drafted still just proved which answers work. Submitting also counts as validation in the consolidator's eyes, whoever drafted the text: the user read it and put their name on it. The page stays editable afterwards (the text is a reuse corpus) — what stops is the relay, since an APPLIED row's edits are housekeeping.

**Drafting runs in the walkthrough job-arm**, not as a Hank tool: the state machine calls the [`applicationDraftingSubAgent`](../src/server/subagents/registry/applicationDrafting.ts) sub-agent and persists into `JobInteraction.coverLetter` / appends `{question, answer}` to `shortAnswers`. It writes from the role's full attribute block, the posting, the parsed résumé verbatim (the same text the critic verifies claims against — not the structured summary), `profile.md` / `resume.md` / `frequent_questions.md`, the company + job notes, and the past-application catalog. **The user's prior letters and answers are the only voice samples it's given** — `profile.md` and `resume.md` are agent-written and supply stated preferences, not voice — so opening the comparable prior application via `read_reusable_application` is the point of the loop, not an optional deep-read. `save_application_answer` (co-write) is the manual write path — `update_job_interaction` does NOT touch drafts. Ashby/Gem/Workday form fetchers hit unauthenticated SPA backends and can silently break — run [`verify-matrix.ts`](../scripts/ats/verify-matrix.ts) on suspicion ([ats-scrapers.md](ats-scrapers.md)).

### Post-draft review (critique-and-revise loop)

After a job's answers are drafted, [`critiqueAndReviseForm`](../src/server/procedures/registry/draftApplication/critiqueAndRevise.ts) runs a **recruiter-lens critic** over the full form before "ready." **It normally stops because a round changed nothing, not because it ran out of rounds** — the cap is a runaway backstop. Two filters decide what it acts on, and everything it declines is reported instead of dropped: whose words the item holds (it never rewrites the user's), and whether a rewrite could settle the issue at all (`resolution`). [`applicationCriticSubAgent`](../src/server/subagents/registry/applicationCritic.ts) sees the JD, the drafted application, the résumé (ground truth), and the candidate's other applications to the same company — but **no user memory** (a "fresh reader who only knows the application," enforced structurally: transform-class, no read tools). It flags (1) anything incorrect/contradictory (unsupported claim, internal contradiction incl. same-fact-two-ways, cross-application inconsistency — all `blocking`); (2) cross-artifact redundancy (`redundancy`, usually `polish`); (3) quality a stranger would notice (`polish`). It never rewrites — for each flagged item the loop re-calls `applicationDraftingSubAgent` with a `revision` input, persists, re-critiques.

Each issue also carries **`resolution`**: `rewrite` (the wording is the problem) or `ask_user` (settling it needs a fact only the candidate has — which of two durations is right, whether a venture is still running). The loop acts on `rewrite` only. Spending a round redrafting an `ask_user` issue hands back the same objection next round, and burning the cap that way is how problems a rewrite COULD have fixed ended up in front of the user. As a forced-tool call it fills a leading private `analysis` scratchpad first (reason-before-decision, needed to catch same-fact-two-ways on DeepSeek). Only not-yet-used items are auto-revised. See [sub-agents.md](sub-agents.md).

**Every issue is written twice, for two readers.** `writerNote` instructs the drafting agent; `userNote` is the same finding addressed to the candidate and is shown to them verbatim. The split exists because the loop can only reword the page, while a large share of real findings turn on a fact only the person has — is that venture still running, where do they actually live — so giving up has to leave something a human can settle. Both fields state a conclusion; the deliberation stays in `analysis`.

### How the loop ENDED is reported; only the findings are stored

**The loop says why it stopped** — `CritiqueStop` on its result: `clean` (a pass raised nothing), `needs_user` (what's left turns on a fact only the candidate has, or is their own writing), `capped` (out of revision rounds with fixable problems open), `stalled` (every redraft call failed), `error`. It is the honest answer to "did it finish, or give up?", which a draft arriving on screen otherwise can't tell you — and the ordinary ending is `needs_user`, not `capped`, so two critique rounds with one revision between them is a *finished* loop rather than a truncated one.

**That reason is said, and never stored.** [`persistApplicationReview`](../src/server/procedures/registry/draftApplication/persistApplicationReview.ts) writes only `{open[], settled[]}`: how one pass ended is a fact the row outlives (the relay drains a settled finding out of `open` without touching any verdict field), and a page that shows "nothing came up" has no way to know when that stopped being true. So the conclusion is said once, in chat, by whoever ran the pass. The critic writes the line about the writing itself (`note` on its output, the `proposalNote` counterpart from the shortlist board): a fixed sentence is the only alternative, and the reader who just went through the writing is the one who can say what's in it.

**Chat carries the count; the page carries the findings.** [`narrateApplicationReady`](../src/server/procedures/registry/walkthrough/narration.ts) frames it as the critic's line, then one sentence naming how it ended and how many things are flagged, then the submit button. It does NOT restate them: each is drawn against the answer it objects to, and the copy in chat is the same words a second time, three paragraphs from the text they're about. `draft_application` and `review_application` tell Hank the same thing in their results — how many and what kind, explicitly **don't list them back** — and his prompt forbids rounding "one thing to check" up to "ready to send".

Only **blocking** findings with a `userNote` reach `open` (a polish note that outlived two rewrites is taste, not a thing to hold a submit on), and each is keyed to the item it's about by `COVER_LETTER_ID` / `questionId()`. That key is what makes the rest work:

- **The page** ([ApplicationView](../src/components/RightPanel/ApplicationView.tsx)) shows each finding against the answer it's about, above that answer's editor, in one of three tones (`FindingTone`). **The open pair follows who wrote the text**: on the user's own words it's a note (danger rule, `!`), an observation about their writing; on Hank's draft it's a question (muted rule, `?`) — he is asking them to settle something, and rendering it as a fault would be showing someone a warning about writing they didn't do. **The third is `answered`**: the words it objected to are gone, so it fades to a muted `✓` and stays put until the relay carries it to him. It does not vanish on the keystroke that settles it — the user is editing the very words it's about, and the reason for the edit disappearing mid-sentence is worse than reading a note that's already dealt with. An answered finding stops counting as an open thread (so it can't hold the submit).
- **A finding is anchored to the WORDS it objects to**, by `atHash` — a hash of the item's text when it was raised. Nothing clears one and nothing marks it resolved: [`partitionFindings`](../src/server/entities/jobs/applicationReview.ts) re-derives open-vs-settled from the current text on every read. Anchoring to the ITEM instead (clear-on-edit) settled a finding the moment the item was touched, so editing and undoing reported two live objections to Hank as answered.
- **Re-reading is Hank's call, and he has to make it.** [`review_application`](../src/server/agent/tools/registry/reviewApplication.ts) → [`runReviewApplication`](../src/server/procedures/registry/draftApplication/reviewApplication.ts) enters the same loop without drafting first; the loop leaves the user's own sentences alone, so "look at it again" can't become "rewrite what I just wrote". His prompt says nothing re-reads on its own, so a verdict from before the user's edits describes text that no longer exists.
- **Rewriting an item settles its findings** — the objection was to text that no longer exists — and settled ones stay on the page in the muted tone until the relay carries them. Putting the original wording back un-settles them, because the words they were about are back.
- **Submit asks once.** With anything still open, the submit button surfaces the count and defers; a second tap marks it applied regardless. It's the last honest moment to catch a contradiction, not a gate.
- **Settled findings ride the edit relay**, then drain. Paired with the diff they say what question the user was answering — which the consolidation pass turns into a `resume.md` / `profile.md` fact so the next draft doesn't get it wrong again.



### Chat co-writing (the `ask_user` hand-off)

When the decider returns `ask_user`, the job arm hands off to collaborative chat — but **only after putting what it DID draft on screen**: the two halves are one pass ("here's what I wrote, here's what I couldn't"), and leading with the ask alone read as though nothing had been written. Then it emits the opening listing the needed items and waits (`wrappedUp:false`). **No marker** (focus is ephemeral). Hank shapes each reply into an answer with [`draft_application_question`](../src/server/agent/tools/registry/draftApplicationQuestion.ts), passing what they said as `extraContext`; [`save_application_answer`](../src/server/agent/tools/registry/saveApplicationAnswer.ts) is only for text they dictate verbatim. To continue/finish, re-enter the job (`work_on_job` or the next-role picker): the job arm re-runs the draft procedure, which re-derives what's still pending from `JobInteraction.draftDecision` (re-emitting the opening for the remainder) until everything's answered and it falls through to submit — completion is inferred, no "done" tool. The how-to guidance is a static `CO_WRITE_GUIDE` section in [hank/system.ts](../src/server/agent/hank/system.ts) (Hank gets the specific items from the opening + `view_application_questions`), rather than a per-turn injection. **Not yet handled:** bespoke/unsupported forms don't trigger co-write.

### Dual-write + the reuse flag

**`coverLetterReuse` / `shortAnswersReuse[i]` is the only state a draft artifact carries beyond its text**, and it answers one question: may we reuse this when drafting later? Only `true` counts; `false` and `null` both exclude, and it gates [`loadPastDrafts`](../src/server/entities/jobs/pastDrafts.ts) (the voice corpus). Every agent write clears it. It turns on from exactly three gestures, all made **on the application page**: editing an item, pressing Copy on it, or the switch itself. Nothing in chat sets it — a flag the user can't see change is one they can't disagree with. It is not the authorship signal (that's the two baselines above); conflating them is what let the switch relabel a draft as the user's.

**Nothing is deleted at APPLIED.** Applying used to wipe every artifact the user hadn't personally edited or copied, keyed on a separate `*UsedAt` timestamp pair. Those columns are gone (migration `20260729120000_drop_draft_used_at`): they never diverged from the reuse flag in prod, and re-keying the wipe onto reuse would have deleted a letter the user wrote and then marked not-reusable — "don't reuse this elsewhere" is not "throw this away". Full detail on the switch: [docs/ui.md → Documents view](ui.md). If you add a draft artifact, mirror the pattern: a parallel `*Reuse` flag, agent writes `false`, user touches write `true`.

### applicationQuestions envelope

Stored on `Job.applicationQuestions` as JSON (full type in [types.ts](../src/server/scrape/types.ts)):

```ts
| { status: "ok"; questions: ApplicationQuestion[]; coverLetter?: boolean; fetchedAt: string }
| { status: "empty"; coverLetter?: boolean; fetchedAt: string }
| { status: "unsupported" }            // URL isn't on a recognized ATS
| { status: "error"; error: string; fetchedAt: string }
```

`null` (unset) = "no fetch attempted", distinct from `{status:"empty"}` ("fetched, no questions"). `{status:"error"}` refetches after 24h. `coverLetter` records a dedicated cover-letter *attachment* (only Greenhouse sets it); `undefined` ≠ "no cover letter" — on other ATSes it shows as a "Cover Letter" *question* caught by `isCoverLetterQuestion`.

**The `null` ≠ empty distinction is load-bearing for every surface that reports form state to the user** — collapsing it is the "Hank confidently said there are no questions" bug (he read a form that had never been fetched). [`loadMergedQuestions`](../src/server/entities/jobs/applicationQuestions.ts) exposes `formNeverFetched` (envelope `null` + no hand-added questions) alongside `formUnavailable` (fetched, unreadable) so consumers can tell "not read yet" from "read, empty" from "couldn't read". Two consumers gate on it: **`view_application_questions`** lazily fetches (via `ensureApplicationForm`) on a never-fetched form before reporting, so it can't render `null` as "no questions" — the derivation itself is [`loadApplicationView`](../src/server/views/application.ts); and **`draft_application`** treats a post-fetch `null` (no apply URL) as unavailable, not "nothing to draft". (There used to be a third — a per-turn focus block in the system prompt. It's gone with the focus slot; Hank now has to read the form to know, which is the point.) The prompt reinforces it: *"Not read yet" is never "no questions"* ([system.ts](../src/server/agent/hank/system.ts) drafting section).

## "What's next?" — the between-things picker

[`runWhatsNext`](../src/server/procedures/registry/whatsNext.ts) walks the rungs (rung 0 is the only LLM call; the section loads under it are pure SQL in [`whatsNextOptions.ts`](../src/server/views/whatsNextOptions.ts)); [`renderWhatsNext`](../src/server/widgets/renderWhatsNext.ts) turns its verdict into chat. [`runChat`](../src/server/procedures/registry/chat/runChat.ts) calls it on **silent entry** (an empty message with no picker dispatch) and on **wrap** (`runChatTurn` reports `{wrappedUp:true}`). A free-text message does NOT enter the picker — it goes straight to Hank; a NAMED switch ("let's do Stripe") is Hank calling `company_walkthrough`. Two outcomes:

| Outcome | When | What `renderWhatsNext` does |
| ------- | ---- | -------------------------- |
| `{kind:"profile"}` | Phase 0 (profile prerequisite) failed | Narrate a brief transition cue, thread the reported gaps into the next turn so Hank opens on specifics. Nothing is persisted — intake is re-derived from the memory slots. |
| `{kind:"pick", options, empty}` | Phase 0 passed | Render the [`next_company_picker`](../src/components/Chat/widgets/registry/nextCompanyPicker/Widget.tsx) widget and stop; user picks → `dispatchNextCompanyPicker` applies focus + status. |

Rendered confirm-first (like the job picker). Sections:

| Section | Contents | Mutation on pick |
| ------- | -------- | ---------------- |
| Immediate | An **owed job** (`status IN OWED_JOB_STATUSES` = `INTERVIEW_DEBRIEF`/`OFFERED`, at any company status) or **opportunity** due — single-sourced with the dashboard "Now" bucket via [`attention.ts`](../src/server/entities/jobs/attention.ts); then ongoing-work companies (`SHORTLISTING` / `APPLYING`) + `OPEN` opportunities, stalest first; then (lowest tier) **stale `WAITING_ON_RESPONSE` jobs** — debriefed roles gone quiet past `STALE_WAITING_DAYS` (14), resurfaced once as a "want to follow up?" nudge. | Owed job / stale-waiting → the picked role becomes the turn's entry target and Hank opens the debrief or follow-up in free chat (no mode is stored); else the picked company becomes the entry target (APPLYING stays). |
| Paused | `status = PAUSED` (all — no timer). Wire key stays `deferred`. | Revive (`PAUSED → APPLYING`, fields cleared) + walkthrough. |
| Backlog | `status IN (READY, NEW)`, READY first, top 10 + "Show more". | Bump → `APPLYING`. |
| Empty CTA | All sections empty. | "Add companies to watchlist" → default flow with a "what kind are you looking for?" opener (doesn't touch APPLYING); Hank then grows the list via `find_companies` / `create_companies`. |

Deterministic except phase 0's sub-agent, gated by a deterministic pre-check (an enriched user pays one Postgres round-trip, zero LLM). Between-companies compaction is handled by bundled actions (`caughtUpCompany`/`closeCompany`/`pauseCompany` each consolidate memory + compact atomically), not a focus gate.

## Profile intake

Profile intake is **not a flow runner** — there is no `enrichProfile/` pipeline and no `currentFlow="profile"`. It's a per-turn prompt switch: [`runChatTurn`](../src/server/procedures/registry/chat/runChatTurn.ts) calls [`isProfileObviouslyEnriched`](../src/server/entities/profile/profileInventory.ts) (one Postgres read, cheap enough every turn) and, when it comes back false, builds Hank's system prompt with the profile-intake body instead of the walkthrough one. The tools are the same registry as always (`read_memory`/`write_memory`/`attach_resume_to_profile`/`commit_profile` + shared CRUD — there's no `read_resume`, since `resume.md` is already in Hank's system prompt every turn). Cold-start (no resume) requests an upload first + `attach_resume_to_profile` → [`mergeResumeIntoBackground`](../src/server/procedures/registry/attachResumeToProfile.ts) (merges it into `resume.md`); a user who'd rather not upload one just describes their background and Hank writes it there directly. Pattern (profile body in [hank/system.ts](../src/server/agent/hank/system.ts)): `write_memory` as facts emerge, probe 1-2 dimensions/turn, recap in prose, then `commit_profile` (no args — it gates the exit).

**Exit (`commit_profile`).** (1) [`runConsolidateSessionMemory`](../src/server/procedures/registry/consolidateSessionMemory.ts) pushes transcript facts into `profile.md`; (2) [`profileEnrichmentCheckSubAgent`](../src/server/subagents/registry/profileEnrichmentCheck.ts) gives the verdict; (3) **pass** → `runCompactSession` (step 1 already consolidated); nothing is cleared — there's no flow column — and `runChatTurn` sees the slots are now full, reports `{wrappedUp:true}`, and the what's-next chooser comes up; (4) **fail** → returns `still missing: X, Y` + suggested probes, and the agent first tells the user in human terms it's almost there and what it needs (not silently firing the next question). There's no "switch to profile" tool: intake turns itself on and off per turn from the memory slots. See [runtime.md](runtime.md).

**Search-as-gateway discipline.** When Hank runs a "find jobs matching the thesis" expansion, output is `create_companies` (+ `enrich_companies`), *not* a shortlist on found roles — each matched job is a pointer to its parent company, and the normal scan surfaces it once focus lands there. If you build a structured `web_search_for_jobs`, plumb it as "feeds the watchlist," not "feeds the shortlist."

## Opportunity flow intake (lead-with-jobs)

When the user describes a recruiter conversation (cold DM, application follow-up, referral, outreach), the agent captures it as an `Opportunity` (the **lead**) and each pitched role as a `Job` + `JobInteraction(PITCHED)` linked via `JobInteraction.opportunityId`. One lead can carry roles at different companies. State-machine details: [lifecycle.md](lifecycle.md#opportunity-lead-with-jobs).

**Compact at a natural pause** (AWAITING/CLOSED/triage done): `compact_summary`. (There's no focus to "clear" — focus is ephemeral; `set_focus` is gone.) **Label honestly** — `Opportunity.label` describes the conversation, not a role; don't reflexively prefix "Inbound from…" (use it only for genuine cold outreach). Follow-up to your own apply sets `sourceJobInteractionId` (its presence IS the not-cold signal).

**Intake recipe:**
1. [`create_contact`](../src/server/agent/tools/registry/createContact.ts) for the recruiter/referrer if new — agency recruiters pass `agency` (string), in-house pass `companyId`, **never both**.
2. [`create_opportunities`](../src/server/agent/tools/registry/createOpportunities.ts) with label, `primaryContactId`, optional `nextStepAt` (auto-emits `CALL_SCHEDULED` + → `SCREENING`), optional `sourceJobInteractionId`.
3. **Per pitched role:** dedupe Job (shared `sourceUrl` → `create_jobs` errors on collision → `update_job_interaction({job, opportunity})` to attach) → resolve Company (watchlist lookup; if absent `create_companies` + `enrich_companies`; fall back to a `companyName` string only when enrich returns `cannot_scrape`) → [`create_jobs`](../src/server/agent/tools/registry/createJobs.ts)`([{opportunity, company, title, ...}])` → `JobInteraction(PITCHED)`, no `SURFACED`.
4. `show_opportunity({opportunity})` → puts the [OpportunityDetailView](../src/components/RightPanel/OpportunityDetailView.tsx) on screen + drops a clickable chip (display only).
5. `write_memory("opportunities/{opportunityId}.md", …)` for lead context; per-contact in `contacts/{name-slug}.md`.

**As it evolves:** new role → re-run step 3; fuller JD / discovered URL → `update_job`; company firms up → `create_companies` + `update_job({job, company})`; user triages → per-job `close_job` / `update_job_interaction` (decline → CLOSED + reason; interested → `read_job_description` → walkthrough); lead events → `log_opportunity_events` (`CALL_HAPPENED`/`NEXT_STEP_RECEIVED`/`CLOSED`). (The *viewed* opportunity is the "looking at lead X" signal — there's no focus to set or clear.)

**No promotion step** — the role is a Job from day one; the user applies via the normal shortlist/draft/submit flow. **Don't close the lead** when one linked job hits APPLIED (the recruiter may still be pitching others). **Recruiter-led Companies don't get unsolicited scan rounds** — enrich still runs, but the agent does NOT walk the company unless asked (the recruiter is the channel). **Already-applied case** (applied direct, then a recruiter followed up): run step 3 + `mark_job_applied`; `applyChannel` defaults to `RECRUITER` for opportunity-linked interactions — pass `'DIRECT'` to preserve "applied direct." Set the Opportunity's `sourceJobInteractionId` to the original applied role.

## Dashboard scope

[`/api/dashboard`](../src/app/api/dashboard/route.ts) is **company-rooted** with a top **opportunities** slice. It lists every watched company, pre-splitting `PAUSED` → `deferred[]`, `BLOCKED` → `blocked[]`, `CLOSED` → `skipped[]`; the rest sit in `companies[]`. Each non-closed company includes active JobInteractions (`SCANNED` or further — `NEW` is too noisy) with the canonical role attributes ([roleAttrs.ts](../src/server/entities/jobs/roleAttrs.ts) — `locationAndArrangement` is keyed `location` on the wire). The `opportunities` slice carries active leads (`OPEN`/`SCREENING`/`AWAITING`), each lead's `jobs[]` filtering `CLOSED`/`REJECTED` server-side. Just before serving, [`flipDueInterviewsToDebrief()`](../src/server/entities/jobs/flipDueInterviews.ts) lazily promotes past-date `INTERVIEW_SCHEDULED` → `INTERVIEW_DEBRIEF` (no cron).

[DashboardView](../src/components/RightPanel/DashboardView.tsx) bins into eight collapsible buckets (`Now` / `In process` / `Not started` / `In flight` / `Watching` / `Paused` / `Blocked` / `Closed`), only `Now` open by default. [CompanyContextView](../src/components/RightPanel/CompanyContextView.tsx) buckets into "In pipeline"/"New"/"Skipped"; [OpportunityDetailView](../src/components/RightPanel/OpportunityDetailView.tsx) mirrors it.

**Status → surface/bucket tables:** see [docs/lifecycle.md](lifecycle.md). When adding a status, update together: the `APPLYING` allow-list + opportunity `notIn` clause in [route.ts](../src/app/api/dashboard/route.ts), `statusTone` in [statusColors.ts](../src/lib/statusColors.ts), and the per-status table in [lifecycle.md](lifecycle.md).

**Empty-row labels.** Companies with zero active interactions render an empty-state hint combining status + scan recency (`emptyHintFor`). `recentJobCount` filters `Job.lastSeenAt >= CompanyInteraction.lastScrapedJobsAt` (jobs that fell off a later scan stop counting); `scrape_jobs_for_company` uses one `scrapeStartedAt` per company for both every job's `lastSeenAt` and `lastScrapedJobsAt` (split into two `new Date()` calls and the `>=` breaks at the millisecond boundary).
