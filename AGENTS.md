# Hank

A chat-first job application tool. Two surfaces in one page: chat panel left, mode-switching right panel (dashboard / company-context / job-detail / opportunity-detail). The agent drives a company-walkthrough flow through the user's watchlist, plus an inbound-opportunity flow for recruiter-initiated leads that don't yet map to a known company.

> **v0** = multi-user via Auth.js (Google/GitHub OAuth), bytes-in-Postgres for files (no R2/S3), one chat session per user, no mobile polish. The product loop is feature-complete; the remaining items are infra/scale, not product. Remaining v0 stubs and active project work live in the issue tracker; done work lives in `git log`.

## Where to look

- **Project tracking:** v0 shortcuts to swap for prod (file storage, model lineup, SPA scrape, Resend re-enable), deferred features, mobile polish, and infra all live in **the issue tracker**. Done work lives in `git log`. (There's no roadmap doc — don't link one.)
- **Unfinished refactors:** [docs/INCOMPLETE_MIGRATIONS.md](docs/INCOMPLETE_MIGRATIONS.md) — the single index of every half-done migration, compat shim, and name-that-lies. **Read it before you trust a `// legacy` comment, and add to it if you're about to leave one behind** ([Finish the refactor](#finish-the-refactor-dont-leave-a-tombstone)). If it's not in that file, it shouldn't exist.
- **Schema:** [prisma/schema.prisma](prisma/schema.prisma) — Postgres via Prisma 7.
- **Chat entry point:** [src/server/agent/runtime/runUserMessage.ts](src/server/agent/runtime/runUserMessage.ts) — the function the `/api/chat` route invokes per user message. It owns THE RUN and nothing else: the key gate, the concurrency claim, the `AbortController`, the `runId`. Then it hands the whole message to [`runChat`](src/server/procedures/registry/chat/runChat.ts) and relays what comes back.
- **What a message MEANS:** [src/server/procedures/registry/chat/](src/server/procedures/registry/chat/) — the chat **procedure**, and the top of the product. [`runChat`](src/server/procedures/registry/chat/runChat.ts) is the sequence (promote what came due → let a widget submission commit itself via [`dispatchTopLevelSubmission`](src/server/widgets/dispatchTopLevelSubmission.ts) → ask [`renderWhatsNext`](src/server/widgets/renderWhatsNext.ts) when there's nothing to run on → drive turns until one waits on the user → run the segment wrap once if a company ended). [`runChatTurn`](src/server/procedures/registry/chat/runChatTurn.ts) is the ONE turn runner underneath it: it picks Hank's prompt body, decides when the walkthrough state machine drives, and folds each turn's tool outcomes. There is no orchestrator layer and **no persisted flow** — the three flow runners (profile / walkthrough / default) and the `ChatSession.currentFlow` column that picked between them are **gone**: profile intake is a per-turn derived prompt switch (`isProfileObviouslyEnriched`, a Postgres read), and "default" was never a flow — just Hank with a thinner prompt.
- **Chat runtime:** [docs/runtime.md](docs/runtime.md) — the run-vs-message split, `runChat`'s order of operations, `runChatTurn`'s two paths, the handoff invariant, the deterministic `runWhatsNext` rung walker, bundled "managed" mutation actions, the widget event protocol, and the procedure + sub-agent inventories. Closest thing to a "behavior spec." **There is no flow state at all** — no runner registry, no mode column; the walkthrough is a procedure entered on an explicit trigger, and profile intake is a per-turn prompt switch. **Focus is likewise ephemeral — there is no focus slot** (removed on the ephemeral-focus branch): the walkthrough state machine dispatches on an in-memory `entryTarget` threaded from widget payloads + handoff tools, every switch drops a clickable `focus_ref` chip, and in free chat Hank re-supplies a slug. The old side-trip detection / `pausedWalkthroughCompanyId` / "Resume walkthrough?" round-trip is gone. See [docs/architecture.md → Focus vs panel view](docs/architecture.md). (Growing the watchlist is not a flow — Hank does it via `find_companies` / `create_companies`, and the `company_checklist` submission is dispatched at the top level of `runChat`.)
  - **Invariant — nothing runs unless Hank hands off.** The deterministic walkthrough state machine advances **only** on an explicit trigger: a `handoff: true` tool Hank called that turn (`company_walkthrough` / `work_on_job` / `find_companies` / `scrape_jobs_for_company` / `show_whats_next` / `commit_shortlist` — entries into a sequence; `commit_shortlist` is the one that also writes, because committing the board IS entering the walkthrough's continuation), a user **widget submission**, or a **silent entry** (deterministic continuation after a pick). A plain conversational turn where Hank just chats runs **nothing** after his reply. There is no behind-his-back re-derivation (the old always-re-run-then-suppress-with-heuristics model — pure-conversation guard, side-trip machine-suppression — is gone). The paired legibility rule: deterministic work that *does* run (wrap consolidation + compaction) is **relayed** to Hank via a Hank-only `pipeline_activity` note, and the compaction summary is re-injected at the head of his context. So Hank's prompt says "nothing continues after your reply unless you hand off" — never "things happen automatically when focus is set." Full detail: [docs/runtime.md → The invariant](docs/runtime.md) + → Relay, don't hide.

## Commands

All scripts live in `package.json` — `pnpm dev` / `db:migrate` / `db:generate` / `db:seed` / `db:studio` / `usage`, plus the audit harnesses. `pnpm usage` summarizes `TokenUsage` rows; **every `db:*` command and `scripts/` run hits prod** — see "Which database are you hitting?" below.

**Formatting and lint are separate jobs and never overlap.** `pnpm format` (Prettier, `printWidth: 80`) owns all whitespace/wrapping/quotes; run it before committing. `pnpm lint` (ESLint 9 flat config, [eslint.config.mjs](eslint.config.mjs)) owns correctness only — type-aware bug-catchers (`no-floating-promises`, `no-misused-promises`, …), import discipline (`import-x/order` is auto-fixable via `eslint --fix`), the `no-await-in-loop` perf rule, and the architecture DAG (`eslint-plugin-boundaries`). `eslint-config-prettier` sits last so the two never fight. Errors must be zero to merge; the remaining ~260 are advisory **warnings** to chip away at (`prefer-nullish-coalescing`, `no-non-null-assertion`, …), not blockers.

**Data migrations are SQL in `prisma/migrations/`. Reaching for a script instead is the exception, and the bar is higher than it looks.** A `prisma/migrations/` entry is one file, one chain, one command: `pnpm db:migrate` applies it and `_prisma_migrations` records it. A script is two of each plus a gate migration to tie them together, and the apply order is a trap — run the gate before the script and the migration fails, which is exactly what happens in practice.

**The test is not "would app code be easier to write." It's "can SQL express this at all."** Postgres has `regexp_replace`, `jsonb_array_elements`, `DISTINCT ON`, lateral joins, and `DO $$` blocks; between them they cover string munging, JSON surgery, dedup, and conditional logic. A transform you'd write in TypeScript because it's more familiar is still a SQL migration. Only three things genuinely force a script — reaching for a **secret** (decrypting with the master key), calling **out of process** (an LLM, an HTTP fetch), or re-running a **parser** that only exists as app code. If you can't name which of those applies, write the SQL.

  - **"But it has to match a TS function exactly" is not a reason — it's a thing to solve in the SQL.** Define the shared expression ONCE as a `pg_temp` function and call it on both sides of whatever join needs it; then the two halves can't drift, which was the whole worry. Verify by running the migration inside `BEGIN … ROLLBACK` against real data and diffing the counts before you ship it.
  - **A script that IS justified gets a paired `prisma/migrations/` entry asserting its work landed** (`RAISE EXCEPTION` naming the exact command) — Prisma has no script-based migrations, so that assertion is what keeps `prisma migrate status` the single answer to "is everything applied?". See [scripts/migrations/README.md](scripts/migrations/README.md) → "Every script is paired with a gate migration".
  - Scripts that clear the bar live in **[scripts/migrations/](scripts/migrations/README.md)**: dated, dry-run by default, and **deleted once applied** (the README keeps the ledger). It's the one directory you can skim past; nothing in `src/` imports from it.

## Conventions

- **One name per concept; names carry the meaning, comments fill the gaps.** Assume the reader knows how to read code but nothing about this codebase — they should follow it from the variable / function / parameter names alone, with comments reserved for the genuinely non-obvious (a *why*, a gotcha, an invariant), never to re-explain what a good name would have said. So don't give one thing two names: the same concept keeps the **same word everywhere**, varying only by the casing its position demands. Concretely for agent tools, the registry **filename**, the exported **const**, and the tool's **`name:`** string are one name in three casings — `markJobApplied.ts` → `markJobAppliedTool` → `"mark_job_applied"` (never `markApplied.ts` for `mark_job_applied`; never a `promoteResume.ts` holding `attach_resume_to_profile`). The const suffix is always `Tool`, never `ToolDef` — `ToolDef` is the *type* ([tools/lib/types.ts](src/server/agent/tools/lib/types.ts)), so a `blockCompanyToolDef` const reads like a type when it's a value. The same discipline holds outside tools: a param, its schema field, and the id/entity it resolves to share a name. When you catch yourself writing a comment to explain what something is, first ask whether a rename removes the need for the comment. Tool-registry specifics: [docs/tools.md](docs/tools.md).
  - **Sub-agents and procedures follow the same three-casings rule — sub-agents with a `SubAgent` suffix (exactly like tools' `Tool`), procedures with a `run` prefix.** A sub-agent's registry **file**, its **exported def**, and its **`name`** (which IS the `TokenUsage.operation` key) are one name: `scanJob.ts` → `scanJobSubAgent` → `"scan_job"`. A procedure's **file/folder** and its **entry export**: `wrapCompanySegment.ts` → `runWrapCompanySegment`, `preScan/` → `runPreScan`. The `run` prefix is what marks the entry point among a folder's helper exports (`loadPreScanContext`, `mergeChunkVerdicts` are steps, not entries) — so a folder has exactly ONE `run<FolderName>`, and a second entry into the same procedure is named for what it does (`runChecklistAdd`). A generator entry's drain-to-completion wrapper is `<entry>Collect` (`runDraftApplicationCollect`). The failure this prevents is real and was everywhere before: `compactSummary.ts` exporting `runSummaryPass` and metering as `compact_chat` meant one sub-agent went by three names, so grepping any one of them found a third of its call sites. (A sub-agent stopped being a function when it became a `SubAgentDef` object — nothing is named `run<SubAgent>` anymore, because the only thing that runs one is [`runSubAgent`](src/server/subagents/lib/runSubAgent.ts).)
- **A comment describes the code that's here. Git describes how it got here.** A comment earns its place if it changes what a reader DOES with the code in front of them, and three tests catch the ones that don't. **Tense:** is it about this code, or about code that isn't here? Anything past-tense about a removed shape — "the old X", "this used to", "replaced by", "N was retired in the … overhaul" — is a commit message in the wrong file, and `git log -S` finds it better than a comment does. **Adjacency:** can a reader confirm it from this file? If checking means opening three others, it's a doc pointer, not a comment. **Compression:** state the constraint in one sentence; if an anecdote (a date, a company name, a row count, a quoted model output) is doing the persuading rather than the rule, cut the anecdote.
  - **The conversion, not the deletion, is the point.** A genuine "don't reintroduce X" keeps its constraint and loses its incident: *"The old past-skip-pattern input was removed 2026-07: it created a feedback loop where one wrong LOCATION_MISMATCH close became authoritative evidence, snowballing (Databricks accumulated 264 location-closes this way)"* → *"It does NOT look at this user's past AUTOMATED decisions — feeding a verdict back in as evidence lets one wrong close snowball into the next."* Present tense, one clause, and it can't rot, because it describes a scope the file still has.
  - **What STAYS**, so this doesn't swing into underdocumentation: a *why* for a line that looks wrong (`// forced tool_choice 400s with thinking enabled`), an invariant a caller can silently violate, an external constraint (Ashby's `isRemote` lying, Greenhouse's questions endpoint 404ing, the React Compiler purity workaround), and units / ordering / formats a name can't carry. **Dates stay on EXTERNAL facts** — pricing as of, API docs as of, a model-pin's audit score — where they say how stale the fact might be. Dates on our own changes go.
  - **Two smells worth naming.** A ticket ref (`HANK-391`) is a pointer to context the comment should just carry; every one in this repo sat beside prose that already explained the point, so they were all removed. And a file-header essay restating `AGENTS.md` or a `docs/` page is the adjacency test failing — link the doc instead.
- **[src/utils/](src/utils/) is the app-blind helper zone — a function goes there when it knows nothing about Hank at all.** Same axis as `platform/` but one level up: `utils/` may not name a company/job/opportunity/contact OR any app concept (impersonation, focus, widgets, statuses), and it imports nothing from the repo except other `utils/` modules — so it's importable from client and server alike. **[src/lib/](src/lib/) is the tier above it**: shared client/universal code that DOES know the app (`chatStore`, `theme`, `statusColors`, `companyLogo`, `impersonation`, `widgetKinds`).
  - **The test is "could this realistically be called from a completely different part of the codebase?" — not "is it called twice yet."** A single caller is fine; `utils/` is allowed to be a bit of a drawer. What keeps it honest is the domain-blindness bar, not scarcity. So a generic `chunk<T>` hiding in a pre-scan file as `chunkJobs`, an FNV-1a hash inlined next to the thing it hashes, or a fourth hand-rolled relative-time formatter all belong here — while a helper whose *thresholds or shape* only make sense for its one call site (a heatmap's level buckets, a physics canvas's px↔metre scale) stays local.
  - Fifteen modules: `abort.ts` (`isUserAbortError` — the one predicate for "the user hit Stop", shared by the chat turn loop, the sub-agent lib, and the scan fan-out) · `now.ts` (`nowMs`/`nowDate`/`nowPerfMs` — the one copy of the React-Compiler purity workaround) · `random.ts` (`randRange`, same workaround for `Math.random`) · `text.ts` (`truncate`/`truncateStart`, `normalizeForCompare`, `initial`, `indent`, `titleCaseSlug`, `looksLikeAcronym`) · `date.ts` (`relativeTime`/`relativeAge`, `fullDate`/`shortDate`/`shortDateTime`/`fullDateTime`, `startOfLocalDay`, `dayKey`) · `format.ts` (`money`, `humanBytes`, `count`) · `guards.ts` (`isRecord`, `as*`, `isScalar`, `stringField`) · `json.ts` (`tryParseJson`, `prettyJson`) · `array.ts` (`chunk`) · `html.ts` (`escapeHtml`/`unescapeHtml` vs `decodeEntities` — read the header, the entity ORDER differs on purpose) · `markdown.ts` (`splitSections`) · `hash.ts` (`fnv1a`) · `encoding.ts` (`base64UrlToBytes`) · `browser.ts` (`isStandalonePwa`) · `url.ts` (`normalizeUrlInput`, `urlHost`/`urlOrigin`, `withQueryParam`).
  - What forced this: `nowMs` existed verbatim in 12 files, `money` in 4, `isRecord`/`isObj`/`isObject`/`isPlainObject` in 6, `truncate` in 4 under three names, and four hand-rolled relative-time formatters had quietly drifted apart.
  - **`platform/slug/` and `platform/time/` are pure and domain-blind too, but stay in `platform/` for now** — they're already properly homed, and moving them is a bigger structural call than this pass. Don't take them as counter-examples to the rule above.
- **Server code lives in [src/server/](src/server/), and the one axis that orders it is: does this code know what a job or a company is?** Everything that does NOT is infra (`platform/`, `auth/`, `db/`); everything that does is domain, split by what it's for — the LLM agent engine (`agent/`) · isolated sub-agents (`subagents/`) · **reusable multi-step procedures (`procedures/`)** · the domain model itself (`entities/`) · **the payloads its surfaces render (`views/`)** · domain services (`memory/`, `scrape/`, `widgets/`). A folder that straddles the line gets **split**, not filed under whichever half is bigger — that's why there is no `files/` or `slug/` folder: the byte store went to `platform/storage/`, the resume to `entities/`; the string slugifier + collision-retry minter went to `platform/slug/`, the four entity resolvers to `entities/resolveBySlug.ts`. Same rule kept `scrape/` out of `platform/` (an ATS parser is the most domain-specific code in the repo) while `scrape/headless.ts` — a bare Playwright singleton — moved to `platform/browser/`.
  - **`agent/` splits on what a piece of the agent *is*, not on when it runs.** Six subfolders: **`hank/`** — the agent's DEFINITION (`system.ts` prompt, `toolset.ts` = which tools he's handed, `model.ts`, `profileContext.ts`); **`tools/`** — the tool DEFINITIONS (`registry/` one file per `ToolDef` + `lib/` abstract tool infra); **`runtime/`** — how a turn EXECUTES (`runUserMessage` opens the run → `runHankTurn` runs one Hank turn → `runAgentTurn` streams it and dispatches its tools, plus `streamingCore` and `stopRegistry`); **`session/`** — the chat transcript store (`chatSession.ts` lifecycle, `loadTranscript.ts` replay+repair, `appendMessages.ts` writes, `narrate.ts` status/prose lines, `uiProvenance.ts`); **`runTree/`** — run-tree capture for `/admin/runs` (`captureTurn`, `traceAccumulator`, `ids`); and **`contracts/`** — the vocabularies the agent and the deterministic layer share (`UiEvent`, `EntryTarget`, and the event unions in `events.ts`). The dependency runs one way, `runtime/` → `hank/`, never back: swap the definition and the machinery is untouched.
    - **`runtime/` is the one part of `agent/` that may not know what a company is.** `tools/` and `hank/` are drenched in domain and should be — they're the DEFINITIONS. `runtime/` is the machinery, and the bar is mechanical: **no import from `entities/`, `procedures/`, or `widgets/`, no prisma query, and no branching on the contents of a domain value.** It may TRANSPORT one (a `StreamEvent` carries `UiEvent`s; `runAgentTurn` hands back each tool's raw `ToolResult`) — it just may not read it. The single sanctioned exception is `runUserMessage` importing `runChat`, which is the hand-off itself. What this rule bought: the old `runChatTurn` imported `runWalkthrough` and ran a raw `companyInteraction.findMany`; folding "which tool ended a company" happened two layers below anyone who knew what that meant. If you're about to add a domain import here, the code belongs in `procedures/registry/chat/`. Note the deliberate `hank/toolset.ts` vs `agent/tools/` distinction — WHICH tools vs WHAT they are; don't collapse them back into two things both called "tools".
  - Every isolated-LLM-call sub-agent (prompt + context + output parser) lives in [src/server/subagents/registry/](src/server/subagents/registry/) — one file per sub-agent (a folder-per-name only for a genuinely multi-file one; none currently is); the shared sub-agent harness lives in [`subagents/lib/`](src/server/subagents/lib/), co-located with the sub-agents it serves: `types.ts` (the `SubAgentDef` contract), `runSubAgent.ts` (the one runner), `readTools.ts`, `subAgentRun.ts` (the capture). So `subagents/` itself holds nothing but `registry/` + `lib/` — same shape as `agent/tools/`, down to the types-vs-machinery split.
- **There is no "pipeline" layer and no tier-1 "flow" type. `procedure` is the one specific term** (never call a procedure a "workflow"). A **procedure** ([src/server/procedures/registry/](src/server/procedures/registry/), one folder per procedure — so `procedures/` holds only `registry/`) is a reusable multi-step chain — deterministic steps + `subagents/` calls — invoked by EITHER the chat runner OR a Hank tool. The chat runner is itself one of them ([`registry/chat/`](src/server/procedures/registry/chat/)): it's entered from `runUserMessage` rather than a tool, but it's the same shape — deterministic steps chained over sub-agent calls — and putting it here is what lets `agent/runtime/` stay domain-blind. Convention: a thin tool wrapper AND a thin runner call both delegate to the one procedure fn; no orchestration trapped in a tool handler (mirror `procedures/registry/shortlist/` + `procedures/registry/draftApplication/`). Procedure-specific deterministic steps co-locate inside the procedure's folder (e.g. `registry/draftApplication/ensureApplicationForm.ts`); genuinely-shared leaves stay as domain primitives (`entities/`, `scrape/`, `memory/`). **The write half of a sub-agent call is always procedure-specific**: a step that takes one `SubAgentDef`'s output type and persists it (`scan/applyScanMatch.ts`, `scan/applyJobEnrichment.ts`, `enrichCompanies/applyLogoVerdict.ts`, `shortlist/seedBoardStances.ts`, `enrichCompanies/commitHuntedUrl.ts`) can only ever have the one caller that made the call, so it belongs beside it — importing a `subagents/registry/` result type into `entities/` is the tell that a step is filed in the wrong place. It still goes THROUGH the shared write seams (`logJobEvents`, `companyStatusFields`) — co-locating the step is not licence to hand-roll the mutation. The walkthrough state machine is a procedure too: [`procedures/registry/walkthrough/`](src/server/procedures/registry/walkthrough/) (entry `stateMachine.ts`, one file per arm). "Flow" is now only an informal word for a user-facing sequence — it names no type, column, or directory. The `entities/` root holds exactly one cross-entity file — [`resolveBySlug.ts`](src/server/entities/resolveBySlug.ts), the four slug→id resolvers every tool handler opens with. Everything else that used to pile up there was a surface payload and now lives in [`views/`](src/server/views/) (next bullet). Note the split pair: [`views/whatsNextOptions.ts`](src/server/views/whatsNextOptions.ts) is the pure between-things read, while the rung-0 profile gate on top of it costs an LLM call and is therefore a procedure, [`procedures/registry/whatsNext.ts`](src/server/procedures/registry/whatsNext.ts). (The `enrichCompanies/` procedure — `enrichCompanies.ts` (the worker pool) over `enrichOne.ts` (the per-company chain) + `runChecklistAdd.ts` — is the work-out-who-a-company-is chain the `find_companies` checklist, the `enrich_companies` tool, and the walkthrough's on-entry backfill all feed. It does NOT scrape: pulling roles in is a separate step that runs after a company is enriched.)
  - **`pipeline_status` / `pipeline_widget` / `pipeline_activity` survive as PERSISTED BLOCK-TYPE STRINGS only.** They're written verbatim into `ChatMessage.content` JSON and read by the client, so renaming them needs a data migration and would break replay of existing history. They are not evidence of a pipeline layer — there isn't one. (`run_error`, written by `runUserMessage` when a run throws, is a later sibling on the same channel and IS named for what it is.)
- **`entities/` vs `procedures/`: an `entities/` function completes in one uninterrupted await. A `procedures/` function does not.** That's the whole line, and it's mechanical rather than a judgment call. Exactly two things break "one uninterrupted await," and they're the two that matter operationally — both are slow, both cost money or user attention, both are abortable, both need a `RunContext`: **it calls an LLM**, or **it yields to the user mid-flight**. Everything else follows. An entities call is safe inside a `$transaction`; a procedure call never is.
  - **Four checks, all greppable.** (1) `entities/` may not import `subagents/lib/runSubAgent`. (2) `entities/` may not export a generator (`function*`). (3) `entities/` may not import from `procedures/` **or `views/`** — **the dependency runs one way**, tools → procedures → views → entities → platform, with no back-edge. (4) Every `procedures/` entry is `run<Name>` and takes a `RunContext`. Checks (1) and (3) — the import back-edges — are now **lint-enforced** by `eslint-plugin-boundaries` in [eslint.config.mjs](eslint.config.mjs) (an `entities/` import of `views/`/`procedures/`/`subagents/`/agent code is an error); (2) the generator ban and (4) the naming rule are syntactic/nominal and stay convention-only.
  - **Do NOT use "spans multiple domains" or "combines multiple atomic operations" as the test.** Neither discriminates. `logJobEvents` correctly imports companies for the milestone dual-write and `commitShortlist` imports jobs, while `verifyCompanyLogo` is a single-domain procedure. And `closeCompany` — a bulk job close + a company status flip + two company events in one transaction — is the most multi-step thing in `entities/` and belongs there: **a coherent set of WRITES is a mutation, not a chain of steps.**
  - **Entities return FACTS; procedures own the prose.** A domain write returns what happened (`{closedJobCount}`, the status that actually landed) and never a user-facing sentence or a `UiEvent`. The two audiences are genuinely different — a tool's `content` is written for Hank, the walkthrough's `pipeline_status` is written for the user — so fusing them into one `narration` field produced a string that fit neither. The formatters live with their one consumer: [procedures/registry/walkthrough/narration.ts](src/server/procedures/registry/walkthrough/narration.ts).
  - **A tool may ENTER one procedure; a tool may not SEQUENCE procedures.** Nine tools call a procedure directly and that's correct — it's the documented thin-wrapper convention. What's forbidden is orchestration in a `handle()`, which is the same rule as "call ONE domain function," one layer up.
  - **The one-await rule says what CANNOT be in `entities/`. It does not say what belongs there — for that the test is: is the shape dictated by the DOMAIN, or by ONE CONSUMER?** A function that reads one table, completes in one await, and passes every check above still doesn't belong here if its row shape, cap, and ordering exist only because one caller wanted them that way. That's the caller's read model and it lives with the caller. The worked example is Hank's watchlist hint block ([`agent/hank/watchlistContext.ts`](src/server/agent/hank/watchlistContext.ts)): one `companyInteraction.findMany`, but "switchable" is not a company-domain concept, and the cap + the stalest-first ordering exist only because a system prompt is rebuilt every turn. Filed under `entities/companies/`, it drifted the predictable way — `hank/system.ts` re-declared the row type locally, so one shape had two definitions. Prompt-context loaders belong in [`agent/hank/`](src/server/agent/hank/) beside `profileContext.ts` and `shortlistBoardContext.ts`; a tool's page size belongs in the tool.
  - **Three things earn a place in `entities/`**, and a file that is none of them is misfiled: a **write** any caller might need (`setCompanyAside`, `logJobEvents`, `markJobApplied`, `commitShortlist`) · a **rule or invariant** (`companyStatusFields`'s clear-on-transition, `jobEventStatus`'s event→status map, `questionsRefresh`, `roleAttrs`, `shortlistPool`'s pool predicate) · a **vocabulary the product offers** (`JOB_CLOSE_REASONS`, `COMPANY_PAUSE_REASONS`, `ALL_LEAD_STATUSES`, `NARRATIVE_DOC_PATHS`). Vocabularies live in the entity's ONE `*Inputs.ts` — never a second file per consumer, which is how `ALL_COMPANY_STATUSES` ended up in a `companyListing.ts` apart from the `SETTABLE_COMPANY_STATUSES` it sits next to now. A read whose shape is set by the screen that renders it is the fourth thing, and it is **not** an entity — it's a view.
- **[src/server/views/](src/server/views/) is the payload of one named surface — and the dependency runs ONE WAY: `views/` may import `entities/`, and nothing under `entities/` may import `views/`.** A view is named for the surface it feeds — a page, a panel, a picker, a board — never for an entity or an operation: the three detail pages ([`getFocusedCompany`](src/server/views/getFocusedCompany.ts) / [`getFocusedJob`](src/server/views/getFocusedJob.ts) / [`getFocusedOpportunity`](src/server/views/getFocusedOpportunity.ts), each owning the payload type it returns), the board ([`shortlistBoard.ts`](src/server/views/shortlistBoard.ts)), the picker ([`whatsNextOptions.ts`](src/server/views/whatsNextOptions.ts)), the Documents and Analytics pages ([`documents.ts`](src/server/views/documents.ts) / [`analytics.ts`](src/server/views/analytics.ts)), and the dispatcher that routes to them ([`showEvents.ts`](src/server/views/showEvents.ts) — `buildShowEvents` loads a detail view + emits the `show` / `panel_mode` SSE events that move the right panel).
  - **The one-way rule is the whole point, and it is what tells you where to cut a file.** Anything a write depends on is a domain rule, so it stays in `entities/` no matter how board-shaped it looks: `shortlistPoolWhere` / `onBoardWhere` / `isStanceable` ([`entities/jobs/shortlistPool.ts`](src/server/entities/jobs/shortlistPool.ts)) and `placedVerdict` / `isPending` / the edit relay ([`entities/jobs/boardStance.ts`](src/server/entities/jobs/boardStance.ts)) are imported by `commitShortlist` and `setProposedStance`, so only the *loader* is the view. Same cut on the Documents page: the editable-note allowlist + `saveUserDoc` are [`entities/narrativeDocs.ts`](src/server/entities/narrativeDocs.ts); only `loadUserDocuments` is the view.
  - **"Read-only" is NOT the test** — half of `entities/` is read-only. `listCompanyJobs`, `listJobEvents`, `engagement`, `attention`, `pastDrafts` are entity-shaped reads with several consumers and stay put; a view exists because a screen wanted that shape.
  - **A prompt-context loader is not a view either.** `agent/hank/watchlistContext.ts` and `shortlistBoardContext.ts` are shaped by Hank's system prompt, and they live with their one consumer for the same reason a view lives with its screen.

- **Platform/infra plumbing lives under [src/server/platform/](src/server/platform/)**, grouped by concern: `platform/llm/` — the whole "spin up an authenticated LLM call" story (the `resolveClient.ts` factory + the symmetric `resolveAnthropicKey.ts` / `resolveDeepseekKey.ts` per-provider key resolvers + generic AES `keyCrypto.ts`); `platform/usage/` — token metering (`track.ts` + `pricing.ts`); `platform/storage/` — bytes-in-Postgres (`attachments.ts` over the `Attachment` table, plus `docx.ts`/`download.ts`, see [storage/README.md](src/server/platform/storage/README.md)); `platform/slug/` — the pure slugifier + the generic collision-retry minter (`mintSlug` takes a `write` callback, so it names no table); `platform/trace/` — the sub-agent trace-span vocabulary; `platform/browser/` — the headless-Chromium singleton; `platform/admin/` — the `AdminNote` upsert; plus `platform/time/`, `platform/notifications/` (web-push), `platform/clientEvents/` (browser telemetry). `db/` and `auth/` stay top-level infra pillars.

  **The bar for `platform/` is absolute: nothing in it may name a company, job, opportunity, or contact.** That's the only thing making the folder mean something, and it's load-bearing — the moment a `platform/` module imports from `entities/` or `subagents/`, it isn't platform anymore and belongs on the domain side. (**Lint-enforced** by `eslint-plugin-boundaries` in [eslint.config.mjs](eslint.config.mjs): a `platform/` import of any domain layer — `entities`/`views`/`procedures`/`subagents`/`memory`/`scrape`/`widgets` or agent code — is an error. The "may not *name* a company/job" half stays convention, but the import edge that would let it is caught.)
- **Agent tools are one file per tool under [src/server/agent/tools/registry/](src/server/agent/tools/registry/)** — every `ToolDef` is its own file; the ones Hank can call are assembled by [`hankTools`](src/server/agent/hank/toolset.ts). A few (`fetch_url`, `test_scrape`, `probe_ats`, `read_reusable_application`) are handed only to sub-agents and are deliberately absent from `hankTools` — they still live in the registry, because a reader grepping a tool name should find one file for it wherever it's used. Shared tool infra sits beside `registry/` in [`tools/lib/`](src/server/agent/tools/lib/): `types.ts`, `toolError.ts`, `resolveEntityArg.ts`, and `index.ts` (which derives only `toolAffectsViewedState` from the live set — NOT the registry). So `tools/` itself holds nothing but `registry/` + `lib/`. Add a tool = add a file in `registry/` + one import in `hankTools`. See [docs/tools.md](docs/tools.md).
  - **`tools/lib/` is abstract tool infrastructure ONLY — nothing in it may know anything domain-specific.** The `ToolDef` contract, the error/result shapes, the slug-or-focused input resolver — the machinery every tool uses regardless of what it does. By the same rule three vocabularies moved OUT of `tools/lib/types.ts`, because tools are only one of several producers: `TraceEvent`/`EmitTrace` → [`platform/trace/`](src/server/platform/trace/types.ts) (`scrape/` forwards them and shouldn't have to import upward into the agent layer), and `UiEvent` + `EntryTarget` → [`agent/contracts/`](src/server/agent/contracts/) (`entities/showEvents.ts` and the widget dispatchers emit them without being tools). Domain knowledge — a status/reason **vocabulary** the product offers (`COMPANY_CLOSE_REASONS`, `ALL_LEAD_STATUSES`, `LOG_JOB_EVENT_TYPES`), a domain **input schema** (`ShortAnswerSchema`), a domain **rule** (`needsQuestionsRefresh`), a domain **write** (`createCompanyStubs`) — lives in `entities/<domain>/`, and the tool imports it. A tool's own one-off input schema (the `create_companies` `{name, context}` shape) stays inlined in the tool file. When you're about to add a company/job/opportunity/contact constant or helper to `tools/lib/`, that's the signal it belongs in `entities/` instead.
  - **A tool `handle()` is the agent I/O boundary — thin. Business logic lives in `entities/` or `procedures/`.** The handler does four things and stops: (1) resolve the agent's slugs → ids (`resolve*BySlug`) + parse its local-time strings → `Date`; (2) call ONE domain function; (3) format the agent-facing result string / shape the `toolError`; (4) return. A `$transaction`, DB write, status computation, event→status mapping, clear-on-transition nulling, cascade, or slug mint in a tool file is misplaced — that's the domain's job, so a pipeline/procedure/other tool can reuse the exact behavior. Reference split: [`create_opportunities`](src/server/agent/tools/registry/createOpportunities.ts) (thin) → [`entities/opportunities/createOpportunities.ts`](src/server/entities/opportunities/createOpportunities.ts) (the work). A read tool's `SELECT` + string formatting is presentation (fine to inline), but a genuine read-*model* (deriving item status from a decision + answers; a default-status filter rule) is domain — extract a loader (`listCompanyJobs`) — or, when the shape is set by a screen rather than the domain, a view (`loadApplicationView`, which `view_application_questions` and the application page share).
  - **Reuse before you write a helper.** Before adding a function, grep `entities/<domain>/` + `procedures/registry/` for one that already does it. The write **seams** are deliberately single-implementation — a second copy silently drifts from the first: the timeline-event+status-cache write is `logJobEvents` / `logCompanyEvent` / `logOpportunityEvent` (never `prisma.*Event.create` + a hand-rolled status flip at a call site); the company status write is always `companyStatusFields()` (the clear-on-transition rule — never hand-null the reason columns); stubs/slugs are `createCompanyStubs` / `mint*Slug`. If the behavior is genuinely new, add it to the domain layer and have the tool call it — don't grow the handler.
  - **A multi-row write costs a CONSTANT number of statements, never one per row. This is the single biggest performance rule in the repo** — `no-await-in-loop` is on for `src/` and is not advisory. Every statement against this remote Postgres costs ~35-40ms, so `for (item of items) await …` inside an interactive `$transaction` is what killed a 26-role close: 78 sequential round trips, P2028 on the timeout, every close rolled back.
    - **`prisma.$transaction([...])` is NOT a batch — do not reach for it as the fix.** It reads like one, but with the pg driver adapter each operation is still its own round trip (measured: 50 ops ≈ 1.97s, marginally *slower* than 50 sequential awaits). **`Promise.all` is not the fix either** — it's capped by the connection pool, so N queries cost ceil(N/pool) waves, and it can't be used inside a transaction at all. **Only one statement is flat in N** (50-row `findMany`: 39ms). The numbers live in [db/bulkUpdate.ts](src/server/db/bulkUpdate.ts).
    - **The shape: read once → decide in JS → write in a fixed number of statements.** Uniform rows use Prisma's single-statement APIs (`createMany`, `createManyAndReturn`, `updateMany`, `deleteMany`, `findMany({where:{in}})`). Per-row VALUES — a batch close where every role has its own note — is the one thing Prisma cannot express, and goes through [`bulkUpdate`](src/server/db/bulkUpdate.ts): one `UPDATE … FROM json_to_recordset(…)` per distinct patch SHAPE (normally exactly one), built with Kysely for typed column names and executed on the caller's Prisma transaction. Kysely is a **compiler only** here; it never opens a connection, so atomicity still belongs to the one Prisma transaction.
    - Worked examples: `logJobEvents` / `logOpportunityEvents` go from 3N statements to four. Neither takes a `db: tx` parameter any more — accepting someone else's interactive transaction forces the per-item awaits back. A caller with writes of its own calls `planJobEvents` and runs `plan.write(tx)` inside its own transaction (`setCompanyAside`, `commitShortlist`).
    - **Reads have the same rule.** N slug lookups is N round trips: every resolver in [`resolveBySlug.ts`](src/server/entities/resolveBySlug.ts) is batch-first (`resolveCompaniesBySlug` and friends answer a whole list in one query; the singular form is a one-element call into it), and `readMemories` is the same for memory notes. A tool holding a list must use the batch form.
    - Where sequencing is genuinely required (a retry, a generator drain, an LLM turn loop, a bounded worker pool, paced third-party HTTP), disable the rule on the line and say which it is; `src/server/scrape/**` is exempt wholesale because all of it is the last case. The two surviving deliberate O(N) DB loops are the slug minters, which resolve collisions by attempting the write — pre-checking to batch them would reintroduce the race they exist to avoid; both say so at the call site.
  - **A closed set of fields that travels together gets ONE list, not one copy per shape.** The canonical job attributes (location / department / compensation / employmentType) are the worked example: [`entities/jobs/roleAttrs.ts`](src/server/entities/jobs/roleAttrs.ts) owns the list and derives every shape from it — `ROLE_ATTR_SELECT` (spread into a Job `select`), `toRoleAttrs` (columns → the `RoleAttrs` shape everything downstream spells), `roleAttrColumns` / `roleAttrColumnPatch` (the write direction), `roleAttrPairs` (the `key=value` block an LLM call renders above a posting), `formatRoleAttrs` (the compact " · " line). **Intersect `RoleAttrs` into a type; never re-list the fields** — a sub-agent input is `RoleAttrs & { title: string; … }`. The failure this prevents: spelled out per call site, every site is independently well-typed, so a fifth attribute lands in the schema and silently misses half of them with no compile error. The two hand-mirrored copies that remain are deliberate and named in that file's header (the agent-facing JSON schemas on `create_jobs`/`update_job`, and each ATS provider's field mapping). The open-ended bags (`Job.attributes`, `Job.enrichedAttributes`) are the separate concern next door — see [`attributePairs.ts`](src/server/entities/jobs/attributePairs.ts), whose header states which call sites get which bag and why.
- All user-scoped queries go through `getCurrentUser()` from [src/server/auth/currentUser.ts](src/server/auth/currentUser.ts), which reads the Auth.js session. The Auth.js config lives in [src/server/auth/config.ts](src/server/auth/config.ts); the Next.js 16 Proxy in [proxy.ts](proxy.ts) gates every non-public path on a session (runs in Node.js runtime, so the Prisma adapter works directly — no separate edge config). Admin-only surfaces (`/admin/*` and their APIs) go through `requireAdmin()` from [src/server/auth/requireAdmin.ts](src/server/auth/requireAdmin.ts), which 404s non-admins via `notFound()` so the routes don't advertise themselves.
- Every LLM client instantiation goes through [`resolveLlmClient(userId, opts)`](src/server/platform/llm/resolveClient.ts) — never `new Anthropic(...)` at a call site (the only exception is key-validation test calls in [settings/actions.ts](src/app/settings/actions.ts)). The factory picks the provider + model + key and returns `{ client, model, provider }`; pass that `model` to BOTH `messages.create/stream` and `recordUsage`. It wraps the key resolvers: `resolveAnthropicApiKey(userId)` / `resolveDeepseekApiKey(userId)` return the user's decrypted key, fall back to the server key only when `canUseServerKey=true` (one flag, both providers), else throw `NoAnthropicKeyError` / `NoDeepseekKeyError`. Never read `process.env.ANTHROPIC_API_KEY` / `DEEPSEEK_API_KEY` directly. User keys are AES-256-GCM encrypted at rest via [src/server/platform/llm/keyCrypto.ts](src/server/platform/llm/keyCrypto.ts) under `ANTHROPIC_KEY_ENCRYPTION_KEY`. See **[docs/llm-providers.md](docs/llm-providers.md)** for the provider/model architecture and the "Per-user Anthropic API keys" section below for the gotchas.
- Memory notes addressed by path with optional `companyId`/`jobId`/`opportunityId`/`contactId` FKs. Authoritative list of paths + their purpose lives in [docs/memory.md](docs/memory.md); per-pipeline agents only see the slice they need (the enrich-profile agent owns the writes; the walkthrough agent + the find_companies sub-agent read but don't write). The path validator that gates all writes is in [src/server/memory/paths.ts](src/server/memory/paths.ts) — if you reference a path in any prompt, make sure it's allowed there or the agent will silently fail to write.
- **The main agent references entities by slug, not id.** Every LLM-facing tool param that identifies a company/job/opportunity/contact is a **slug** (`company` / `job` / `jobs` / `opportunity` / `contact` / `sourceJob`, not `companyId` / `jobId`), resolved slug-**or**-id at the top of the handler via `resolve*BySlug` from [src/server/entities/resolveBySlug.ts](src/server/entities/resolveBySlug.ts); tool result strings emit slugs too. Mint at create sites with `mint*Slug` (after any `$transaction` commits — the mint retries on unique-collision). Widget payloads, the in-memory `EntryTarget`, and sub-agent I/O stay cuids; **memory paths are slug-addressed** (`jobs/{slug}.md` etc — no ids shown to the agent). Full convention + what-stays-a-cuid list in [docs/entity-slugs.md](docs/entity-slugs.md) — follow it when adding a tool.
- Events are the audit trail; `JobInteraction.status` is a denormalized cache updated when an event lands. **The one deliberate exception is the repair pair — `update_job_interaction` / `update_company_interaction` — which write the cached status + reason columns directly with NO `JobEvent` / `CompanyEvent`.** That's the point (a bookkeeping fix isn't a thing that happened), so keep them event-free; the cost is that the tool descriptions, their result strings, and the prompt all have to keep saying so, or Hank reaches for a repair when the user means "this just happened". Anything that genuinely happened goes through the event writers ([docs/lifecycle.md](docs/lifecycle.md)).
- **Two event timelines: `JobEvent` (per-role) and `CompanyEvent` (per-user, per-company).** `JobEvent` (physical table `Event`) is the granular per-role log; the company page's "Recent activity" card reads the **`CompanyEvent`** table (NOT a flatten of job events). Write company events **only** via [`logCompanyEvent`](src/server/entities/companies/logCompanyEvent.ts) — never `prisma.companyEvent.create` at a call site. Rule of thumb for a new company-affecting mutation: a **batch** (closes / surfacing / shortlist) collapses to ONE summary `CompanyEvent` at its seam (the per-job `JobEvent`s still fan out); a **per-role milestone** (applied / response / outcome) dual-writes a `CompanyEvent` alongside its `JobEvent` (`logJobEvents` collects these and emits them as one `createMany` inside its own batch); a **company status change** writes a status `CompanyEvent` (there is no longer a parallel markdown `## Status history` note — the CompanyEvent feed is the sole record, and it's agent-readable in the focused-company context). Adding a `CompanyEventType` value: add it to the enum + migration, add a `companyEventLabel()` entry in [statusColors.ts](src/lib/statusColors.ts) (no raw multi-word enums in the UI), and wire the emitting seam through `logCompanyEvent`.
- **Prefer shared primitives in the UI — and extract new ones.** Most right-panel inconsistencies came from the same concept re-implemented per surface and drifting (list expand/collapse, box headers, status bucketing, the `min-width:0` overflow fix). Reach for the existing primitive before writing markup — `statusColor`/`statusTone`, `companyLogoUrl`, `relativeTime`, and the right-panel shared/ pieces (`RecentActivity`/`RecentActivityList`, `useExpandable`). When you'd be copy-pasting stateful UI logic a second/third time, extract it into [src/components/RightPanel/shared/](src/components/RightPanel/shared/) (a hook for logic, a headless-inner + chrome-wrapper for differing chrome) and add a short section to [docs/ui.md](docs/ui.md). See **[docs/ui.md](docs/ui.md) → "Prefer shared primitives"**.

## Dev server

Assume the reference deployment's operator may already have `pnpm dev` running on port 3000. Never start your own on 3000 and never `pkill` / kill an existing dev server — it collides with their session and they can't see your background processes. If you genuinely need to run the app yourself (e.g. to curl an endpoint to verify a fix), start it on a different port via `PORT=3001 pnpm dev` and shut it down before the turn ends.

**HMR is not reliable for server-side TS modules under `src/server/`.** Edits to `src/server/agent/`, `src/server/entities/companies/`, `src/server/entities/jobs/`, etc. do NOT consistently get picked up by the running dev server — it keeps serving the compiled-at-startup version. You won't notice until you see behavior matching the old code AND debug data (TokenUsage rows, event counts, gate errors) confirming the new code path didn't run. When you've edited server-side code that's load-bearing for the next thing the user is about to test, **ask the maintainer to restart `pnpm dev`** before claiming the change is live. UI-only edits under `src/components/` and `src/app/` HMR fine; the rule is for server / agent / sub-agent / orchestrator code. Stateful changes (Prisma client regen, env var change, schema reload, push VAPID env vars) require restart regardless.

## Which database are you hitting? (verify before any write)

**In this project's own deployment, `.env`'s `DATABASE_URL` points at a production Postgres** (Railway-hosted) — the one real users interact with, with no separate local dev DB and no `.env.local` override; `prisma.config.ts` feeds the same `DATABASE_URL` to migrations. So **everything that loads `.env` — the dev server, `pnpm db:*`, every script in `scripts/`, and `psql "$DATABASE_URL"` — hits whatever that URL points at.** When it's a shared/prod DB, a migration or a mutating script is a production change; treat schema edits + bulk writes as prod-facing and prefer dry-run-first scripts (e.g. [scripts/ats/backfill-attributes.ts](scripts/ats/backfill-attributes.ts), which is read-only until `--apply`).

**Verify the host before a write or migration:** `grep ^DATABASE_URL .env`, or read the `Datasource "db": … at <host>` line `pnpm db:migrate` prints before it applies. Don't trust this paragraph over the live `.env` — if the maintainer later repoints it at a localhost dev DB the calculus flips back, so re-check rather than assume.

The sub-agent harnesses stay safe regardless of which DB is live: the audit scripts under [scripts/regression/sub-agents/](scripts/regression/sub-agents/) and the replay script [scripts/shortlist-jobs/replay.ts](scripts/shortlist-jobs/replay.ts) call a real LLM but write nothing — not by a flag, but because a sub-agent writes nothing at all and the harnesses never call the caller-side persist step. See [docs/sub-agents.md → Testing](docs/sub-agents.md) for the pattern.

## Prisma schema changes — three steps, not two

The TS client and the live PostgreSQL DB evolve independently. After editing `prisma/schema.prisma`:

1. `pnpm db:generate` — regenerates the TS client in `src/generated/prisma/` (else the new columns are invisible to the typechecker).
2. **Author a migration file** under `prisma/migrations/<timestamp>_<name>/migration.sql` — write the DDL by hand (`ALTER TABLE … ADD COLUMN …`); this project does NOT auto-derive SQL from schema edits. Match the existing timestamp format.
3. `pnpm db:migrate` — applies pending migrations to the live DB.

Skipping step 3 is the common foot-gun: typechecker happy, dev server boots, but the first query touching the new column fails with `P2022 ColumnNotFound`. Even non-selecting queries can hit it — Prisma adds `RETURNING *` on delete/update. The fix is `pnpm db:migrate`, not code.

When adding NOT NULL to a column with existing data, backfill first in the migration, then alter.

**A schema change that reshapes existing data has a fourth step: backfill the old rows, and run it.** Adding the column is not the migration — the rows carrying the old shape are. Write the backfill as SQL in the same `prisma/migrations/` entry — that's almost always possible, and "app code would be easier" is not the test (see "Data migrations are SQL" above). Only when it reaches a secret, calls out of process, or re-runs a parser does it become a one-shot script in [scripts/migrations/](scripts/migrations/README.md) (dry-run first, `--apply` to write — mirror [scripts/ats/backfill-attributes.ts](scripts/ats/backfill-attributes.ts)). Either way, run it — rather than adding a "mint it lazily when something touches this row" branch to the read path. The lazy branch looks finished and isn't: rows nothing touches keep the old shape indefinitely, and the fallback that reads them can never be deleted. If the backfill can't run yet, the refactor is **not done** — file it in [docs/INCOMPLETE_MIGRATIONS.md](docs/INCOMPLETE_MIGRATIONS.md) and say so when you hand the work back.

**If `pnpm db:migrate` reports "migrations … diverge from the local migrations directory" or "migration X was modified after it was applied" — do NOT accept the offered `prisma migrate reset`** (it drops all data on a shared DB). Instead: cherry-pick the missing migration, or apply the additive change directly via `psql` and hand-insert a `_prisma_migrations` row. When you hand-insert, the `checksum` must be the real SHA-256 of the file (`shasum -a 256 <file> | awk '{print $1}'`) — a placeholder triggers the "modified after applied" error, which also only offers reset. Recovery for a bad checksum: `UPDATE _prisma_migrations SET checksum = '<real sha>' WHERE migration_name = '…'`.

## React Compiler purity lint fires on `Date.now()` / `Math.random()`

`pnpm lint` runs `react-hooks/purity`, which flags impure calls in a render scope **syntactically** — no awareness of server components / async / helpers. So `const now = Date.now()` inside a server component errors. Fix: hoist into a one-line top-level helper (`function nowMs() { return Date.now() }`) — the linter only inspects the call site, not the helper body. Don't add `eslint-disable`. Same for a render-time `new Date()`.

## Working in worktrees

Worktrees under `.claude/worktrees/<name>/` share the main repo's `.env` and Postgres DB but **not** its `node_modules` or symlinks. After `git worktree add`:

1. **Branch off local `main`** (the integration branch). `EnterWorktree` bases on `origin/<default>`, which can lag un-pushed local commits — compare `git log --oneline -3 main` vs `HEAD` and `git reset --hard main` if behind. Cleanest: `git worktree add <path> -b <branch> main`. Symptom of skipping: "the file the user keeps mentioning doesn't exist."
2. `ln -s $HOME/Documents/hank/.env .env` — migrate + dev server refuse to start without `DATABASE_URL`; symlink so secret rotation stays one place.
3. `pnpm install` — separate `node_modules` (else `pnpm db:generate` errors `prisma: command not found`).
4. `pnpm db:generate` — **always**; the generated client is gitignored, so a fresh worktree has none (else ~50 `Cannot find module '@/generated/prisma/client'`). No-op against the DB.
5. `pnpm exec playwright install chromium` — **only if** running the headless ATS scrapers (Shopify / Meta / Google / Netflix) or the full verify-matrix.

The maintainer's dev server (main repo, port 3000) does not pick up worktree edits via HMR — `PORT=3001 pnpm dev` from the worktree and kill it before the turn ends. Migrations/DB writes from a worktree hit the same (prod) Postgres.

**Do not run `pnpm db:migrate` or schema-mutating `psql` from a worktree without asking the maintainer first.** When the shared DB is a prod instance (see "Which database are you hitting?" above), a worktree migration silently mutates the prod schema; an abandoned branch then leaves prod with columns the canonical schema doesn't know about → later `migrate dev` drift. Write the schema edits + migration file, run `pnpm db:generate` for typechecking, and ask the maintainer to apply. (Read-only `SELECT`s and application-row `INSERT/UPDATE/DELETE` are fine — recoverable; a stray `ALTER TYPE` is not.)

# Auth & multi-user

## Auth.js multi-user gotchas

Auth.js v5 (`next-auth@beta`) with the Prisma adapter.

- **Adapter model names are reserved.** `@auth/prisma-adapter` calls `prisma.account`, `prisma.session`, `prisma.verificationToken` by name; the chat "session" is `ChatSession` — don't conflate. Renaming `Session` silently signs everyone out.
- **`allowDangerousEmailAccountLinking: true` is intentional** (Google + GitHub in [config.ts](src/server/auth/config.ts)) — same email across providers = same User; we trust provider email verification. Revisit only if multiple Users could ever share an email.
- **Sessions are DB-backed** (`strategy: "database"`) — role changes take effect next request (no cookie wait); "sign out everywhere" = `DELETE FROM "Session" WHERE "userId"=…`. Don't switch to JWT without weighing the staleness `requireAdmin()` relies on.
- **`getCurrentUser()` returns a session-shaped object** (`id`, `email`, `name`, `image`, `isAdmin`) — not a Prisma User row. Need `createdAt` etc.? Do a follow-up `findUnique`; don't expand the session callback (every authed request pays).
- **Proxy enforces auth; routes can rely on it.** [proxy.ts](proxy.ts) (Next 16's `middleware.ts` replacement) redirects unauthed pages to `/signin` and 401s unauthed API, running in the Node runtime so it imports the full adapter config. A route reachable without a session goes in `PUBLIC_PATHS`.
- **Adding a fourth OAuth provider** is a one-liner: import the provider, add it to the `providers` array, set `AUTH_FOO_ID`/`AUTH_FOO_SECRET`. Then a button in [SignInPanel.tsx](src/app/signin/SignInPanel.tsx) + server action in [signin/page.tsx](src/app/signin/page.tsx).
- **Email/magic-link sign-in is intentionally absent** (needs a verified sending domain we lack); OAuth is the only path. The empty `VerificationToken` model is kept as an adapter convention. Re-enable checklist lives in the issue tracker.
- **Every new user-scoped query needs `where: { userId }`.** User-scoped models carry a `userId` FK or composite PK; global models (`Company`, `Job`, `Event`, `OpportunityEvent`) reach `userId` via FK chains — scope a top-level `Event` query through the parent `JobInteraction`.

# Memory & sub-agents

## Memory + sub-agent gotchas

Read [docs/memory.md](docs/memory.md) for the full inventory of the three "notes" storage shapes before adding a field or path. Four rules:

- **A memory path that throws on write is a silent failure.** If a prompt (pipeline or sub-agent) names a path, make sure [src/server/memory/paths.ts](src/server/memory/paths.ts)'s `validatePath` allows it — else `write_memory` throws "unrecognized memory path" and the agent moves on. Same for the `read_memory` tool description.
- **`MemoryNote` FK columns are denormalized index hints; `path` is authoritative.** `companyId`/`jobId`/`opportunityId`/`contactId` are `ON DELETE SET NULL` (note content outlives the entity). New entity-linked path → add the matching FK column ([docs/architecture.md](docs/architecture.md) walkthrough); back-relation is `memoryNotes` (`notes` collides with the inline field on Contact/Opportunity).
- **A sub-agent is a DECLARATION, not a function: one [`SubAgentDef`](src/server/subagents/lib/types.ts) per registry file, run by the ONE entry point [`runSubAgent(def, input, ctx)`](src/server/subagents/lib/runSubAgent.ts).** Same shape as `ToolDef` + the tool dispatcher, for the same reason — the def says WHAT the call is (`name` = the operation key, `model`, `maxTokens`, `reasoning`, `system`, `userContent`, `readTools`, `outputSchema(s)`, `parse`), the runner owns HOW it executes, and there is no bespoke tier or per-class variant (vision included). **The two arguments are the whole convention:** `input` is the sub-agent's own domain input, and `ctx` is a [`RunContext`](src/server/agent/contracts/runContext.ts) (`userId`, `sessionId?`, `trace?`, `signal?`) threaded ONCE instead of re-declared field-by-field down the call chain — see "One RunContext" below. Nothing about the SHAPE of the call rides on ctx; that is all def. **A caller never resolves a client, names a model, or records usage/runs**; the runner owns `resolveLlmClient`, `recordUsage`, `recordSubAgentRun`, truncation detection, abort propagation, and the trace plumbing. Three orthogonal options shape the call and nothing else does: declare `readTools` (+ raise `maxTurns`, default 1) for a read-tool loop; declare `outputSchema`/`outputSchemas` for a JSON payload or omit them for prose; and declare `reasoning` — the one that's REQUIRED, see below. **Don't re-split this into a helper per class** — as three near-copies they had drifted into three different answers for truncation detection, abort propagation, and rate-limit reporting.
- **Every LLM call declares how it reasons before it answers — `reasoning`, and it is REQUIRED for the same reason `maxTokens` is.** The vocabulary is [`platform/llm/reasoning.ts`](src/server/platform/llm/reasoning.ts): `{mode:"scratchpad", guidance}` · `{mode:"thinking", budget}` · `{mode:"none", why}`. Which one is even AVAILABLE follows from the call: **a forced `tool_choice` is incompatible with extended thinking** (DeepSeek 400s "Thinking mode does not support this tool_choice"), so every sub-agent that emits an output schema forces one and therefore uses a **scratchpad** — a leading private `analysis` field that `runSubAgent` PREPENDS to the output schema(s) from the def's `guidance`. The def supplies only the guidance (what to walk through); the shared "fill this first, then make every other field match" framing has exactly one copy, in `scratchpadProperty`. Real `thinking` needs an unforced call — the main agent ([`hank/call.ts`](src/server/agent/hank/call.ts), tool_choice "auto") and prose-mode sub-agents (`compact_summary`, which sends no tools at all). `none` is for a pure extraction with nothing to weigh (`enrich_job`, `parse_resume`) and has to say why. **Don't hand-write an `analysis` property into an output schema** — that's the drift this replaced: seven divergent copies under three names, while five judgement sub-agents silently had none.
- **Sub-agent classification is a correctness choice — but a prompt-design one, not a mechanical one.** Transform = one-shot, no read tools, forced output schema. Judgement = read-tool loop, narrow read-only tools, output schema as terminator. In code that difference is exactly "did you pass `readTools`". **A sub-agent's output schema is NOT a tool** — `tools` + `tool_choice` is just the API's only JSON-schema constraint mechanism, nothing dispatches it, and it must never be traced as a tool span or written to `TokenUsage.toolName` (hence `SubAgentOutputSchema` / `outputSchema` / `COMMIT_*_SCHEMA`, never `*Tool`). Litmus: "would a perfect version ever want to read something the parent didn't include?" → judgement. Wrong pick reproduces the shortlist sub-agent's pre-tool-loop recall failure.
- **Don't give sub-agents write tools — or write anywhere else in the file.** `SUB_AGENT_READ_TOOLS` is the default; extend by composition. Persist in the parent after the sub-agent returns (`memoryConsolidationSubAgent` returns `writes[]`, `runConsolidateSessionMemory` applies them) — a write tool inside a loop is a foot-gun, and a write in the wrapper around the loop dodges the rule rather than following it.
- **A sub-agent file holds LLM I/O and nothing else** — prompt, `const MODEL`, output schema, input rendering (`userContent`), output parsing (`parse`). No DB reads, no writes, no short-circuit gates, no `dryRun`/`auditContext` harness flags, and **no I/O of any kind: `userContent` is pure and synchronous**, which is what makes that rule mechanical rather than aspirational (it's why the logo verifier's image fetch moved out to `procedures/registry/verifyCompanyLogo.ts` and the consolidator's memory read to `runConsolidateSessionMemory`). Failure policy is the caller's too: a def `parse` may THROW to reject a structurally-wrong emission, but "what to do when the run fails" (throw / fall back conservatively / degrade) lives at the call site. The caller assembles the input (`loadShortlistJobsInput`, `loadApplicationDraftingContext`, `profileInventory`) and applies the result (`applyLogoVerdict`, `seedBoardStances`, `runConsolidateSessionMemory`). Mechanical check: `grep -rn "db/prisma\|dryRun\|writeMemory\|appendMemory" src/server/subagents/registry/` must come back empty. Full rationale: [docs/sub-agents.md](docs/sub-agents.md).
  - **The complement, and the half that drifts: the caller owns everything from `userId` → data; the def owns everything from data → prompt text.** The seam is the last thing that needs I/O, and three tests place any given field: (1) does producing it require I/O? → caller, always; (2) does its result flow anywhere other than the prompt? → caller, because it's domain logic that merely also feeds a prompt (`decideApplicationForm`'s form partition assigns a **persisted** verdict to the fields it removes, so it stays put); (3) otherwise → def. So a def renders a sibling application's `status` into recruiter prose, picks `enrichedSummary` over `rawContent`, and calls `serializeTranscript` on `StoredMessage[]`. **"In the def" means CALLED FROM `userContent`, not DEFINED there**: the renderers stay single-copy in `entities/` (`roleAttrs.ts`, `pastDrafts.ts`, `attributePairs.ts`). What a pre-rendered input costs: a harness that pre-renders what prod renders differently grades a prompt production never sent. (The résumé is the one thing with NO def-side choice left — every prompt takes the whole `resume.md` background verbatim, which is the point of it being one version.)
  - **One loader per sub-agent, named for it.** `load<SubAgent>Input` returns exactly one def's `TInput` (`loadShortlistJobsInput`, `loadApplicationCriticInput`, `loadApplicationDeciderInput`, `loadFindCompaniesInput`, `loadMemoryConsolidationInput`) and lives in that sub-agent's procedure folder; `load<Procedure>Context` returns context shared across a FAN-OUT of N calls, with the per-call input assembled in the procedure (`loadPreScanContext` per chunk, `loadScanContext` per job). Home is the procedure's folder for one caller, `entities/` when shared. A sub-agent whose input needs no I/O gets no loader. **A harness never hand-builds a field the loader computes** — it calls the loader, or supplies the loader's own inputs.

- **One [`RunContext`](src/server/agent/contracts/runContext.ts), threaded, not rebuilt — and it's what makes procedures legible.** `userId` / `sessionId?` / `trace?` / `signal?` / `runId?` / `timeZone?`, declared by procedures as `RunContext & { … }` and taken by `runSubAgent` as its ctx — verbatim, with nothing added on top. Nothing about how a call is SHAPED belongs on ctx; that lives on the def. It's a **structural** contract on purpose — a procedure passes its own `args` straight through (`{ ...args, companyId }`), so there is no ctx-assembling boilerplate at call sites and nothing to keep in sync when a field is added. **Don't re-spell the fields in a new args type; intersect `RunContext`.**
  - **Every field on it is AMBIENT — that's the membership test.** It says who/when/where the work runs, and nothing in the chain branches on it: the code that READS a field is at the bottom (an LLM call, a persisted row, Hank's `# Today` block) and every layer between just forwards it. A value some middle step makes a decision about is that step's own argument, not ctx.
  - **It is assembled at exactly two boundaries and threaded verbatim from there down**: [`runUserMessage`](src/server/agent/runtime/runUserMessage.ts) opening a run, and [`runAgentTurn`](src/server/agent/runtime/runAgentTurn.ts) dispatching a tool (which adds `trace.parentToolUseId` so the tool's children nest under its chip). **`ToolContext` IS a `RunContext`** — plus a required `sessionId`, since a tool only runs inside a chat dispatch — so a handler forwards `ctx` straight into whatever procedure it enters. There is no runner-side shape and no converter: the old `toRunContext(args)` and `ToolContext`'s flat `emitTrace` + `toolUseId` pair are **gone**. If you're about to hand-build `{ onTrace: …, parentToolUseId: … }`, you're re-introducing them.
- **A procedure can bracket itself as a trace SPAN — and that is the only "def-like" wrapper procedures get.** [`withTraceSpan(name, trace, fn)`](src/server/platform/trace/span.ts) for a plain async procedure, `openTraceSpan` + `finally` for a generator (a wrapper can't stay lazy around one). It exists because the run-tree inspector nests everything by `parentToolUseId`, so it showed turn → tool → sub-agent with the procedure that ORDERED those sub-agents invisible in the middle. **A span is not a tool call and is never rendered as one** — the chat's trace renderer flattens spans away, so the user-visible chip is byte-identical (see "Only real tools get tool spans" in [docs/tools.md](docs/tools.md)). Spans no-op wherever there's no parent chip to hang in, which is why the deterministic layer's own generators (walkthrough / shortlist — driven by `runUserMessage`, not by a tool dispatch) deliberately don't open one. **There is no `ProcedureDef` and shouldn't be**: nothing dispatches procedures by name (they're imported by symbol from typed call sites) and a `runProcedure` would own no shared work, so a def would be a name bolted onto a function.

**Wrapping up a stretch of conversation writes memory automatically.** The two session-wrap procedures — [`runWrapCompanySegment`](src/server/procedures/registry/wrapCompanySegment.ts) and [`runCommitProfile`](src/server/procedures/registry/commitProfile.ts) — compose two steps in this order: [`runConsolidateSessionMemory`](src/server/procedures/registry/consolidateSessionMemory.ts) (the [`memoryConsolidationSubAgent`](src/server/subagents/registry/memoryConsolidation.ts) sub-agent over a recent-message window, emitting multi-path writes to `profile.md`, `companies/{slug}.md`, etc., in append / `section` / replace modes) then [`runCompactSession`](src/server/procedures/registry/compactSession.ts) (summarize + truncate the transcript). **Consolidation is not inside `runCompactSession`** — it has to run even when the session is too short to compact, and `runCommitProfile` needs post-write memory for the verdict gate that sits between the two. Debugging unexpected memory changes? Check the wrap trail before suspecting anything else. Tune the prompt in `memoryConsolidation.ts`.

# The agent's voice & the UI boundary

## Hank's chat replies use natural language, not internal vocabulary

Status enums, tool names, pipeline/flow names, `runWhatsNext` rungs, memory paths, "compaction"/token/model jargon, CamelCase entity names — **none of these appear in Hank's chat replies.** Translation is enforced in three places:

1. **Hank's system prompt** ([hank/system.ts](src/server/agent/hank/system.ts)) — the shared preamble's `# Translate, don't parrot` block (global terms) + each per-mode body (PROFILE_BODY / WALKTHROUGH_BODY / WATCHLIST_BODY, mode-specific terms). The common foot-gun: a new term lands in a flow rule but not the translation block.
2. **Sub-agent output-schema fields quoted to the user** (shortlist `reasoning`, the drafting cover-letter body) — bake the no-enum/no-path constraint into the output schema's field description.
3. **Widget payload labels + reasoning strings** — the producing runner/sub-agent owns the language; the widget renders verbatim.

Right-panel `StatusPill`s run raw enums through [`statusLabel()`](src/lib/statusColors.ts) (`STATUS_LABELS` map → "Caught up" / "Not a match" / "No longer listed"; everything else Title-cases). Add an entry for any status whose enum name shouldn't render verbatim.

**Status vocabulary (current):** `CLOSED` = a user/agent closed it (fit dead-end); `DELISTED` = the board dropped the posting itself (user phrasing "came down / isn't listed"; `Job.closedAt` is the posting-gone date). `BLOCKED` = a **technical** set-aside ("couldn't read the board"), NOT a fit judgment — own **slate** tone, revivable, excluded from scans, own dashboard bucket. `OpportunityStatus.CLOSED` is a separate untouched enum.

### Hide the mechanism, not the intent

"Don't parrot internal vocabulary" bans leaking the machinery (gate names, "the verdict", file paths). It does NOT mean silence. When a gate holds the user (e.g. the profile-enrichment verdict gate), Hank surfaces _that it needs more and why_ as its own judgment ("one more thing so I can target this well") — never a system/checkpoint framing, but never mute either. Apply the same split to any new gate Hank sits behind.

### The screen is not yours to draw

Roles, shortlists, and "what's next" pickers are widgets the deterministic layer renders — Hank's chat text must never reproduce one (the failure: Hank typing a checkmarked role menu with invented roles). Three guards:

1. **`# The screen is not yours to draw`** block in [hank/system.ts](src/server/agent/hank/system.ts) — forbids typed picker chrome and emitting the `<system-reminder>` operator marker.
2. **Provenance notes off the assistant channel** — replayed `pipeline_status`/`pipeline_widget` blocks are rendered as a note the model reads as a system record (never as its own prose) by [`buildProvenanceMessage`](src/server/agent/session/uiProvenance.ts): a real `role:"system"` message (DeepSeek's Anthropic-compatible endpoint accepts mid-array system messages — verified). Don't revert to an assistant-authored stage direction (the old `<ui_shown>` envelope / "[Shown to the user …]" framing) — that assistant-channel placement is exactly what got imitated.
3. **`handoff` loop-stop** — a routing tool with `handoff: true` ends the agent loop so there's no free post-switch turn to confabulate. New routing tools set the flag.

The FUZZY "imitates a widget" class (invented role menus) is surfaced by the offline [`detectFabricatedUiRender`](src/server/agent/session/uiProvenance.ts) in both audit harnesses; its one HARD tripwire flags an emitted `<system-reminder>` marker — still forbidden by the prompt even though provenance now rides an untagged `role:"system"` message and no longer injects that marker (so the tripwire guards spontaneous emission, not an echo). There is no longer a runtime sanitizer — moving provenance off the assistant channel removed the echo pressure that duct-tape addressed (a weak model echoing the old `<ui_shown>` tag), so `stripFabricatedUiRender` is gone.

# Data-model conventions

## The agent speaks in slugs, not ids

The main agent addresses companies / jobs / opportunities / contacts by **human-readable slugs**, never cuid ids — a wrong slug (`stripe-senior-software-enginer`) is visibly wrong; a transposed cuid is undetectable. Canonical doc: [docs/entity-slugs.md](docs/entity-slugs.md). Split across two layers: the domain-blind minter in [src/server/platform/slug/](src/server/platform/slug/) and the entity resolvers in [src/server/entities/resolveBySlug.ts](src/server/entities/resolveBySlug.ts).

**When you add or modify an agent-callable tool this is a hard requirement:**

1. **Inputs accept a slug, named for the entity** — `company` / `job` / `jobs` / `opportunity` / `contact` / `sourceJob`, never `companyId` / `jobId` (which invites the model to invent a cuid). Loosen to `z.string()` and resolve at the top of `handle`:
   ```ts
   const r = await resolveJobBySlug(ctx.userId, input.job); // accepts slug OR raw cuid
   if (!r.ok) return toolError("ENTITY_NOT_FOUND", r.message, r.dedupHint);
   const jobId = r.value.id; // use internally exactly as before
   ```
   `resolve{Company,Job,Opportunity,Contact}BySlug` (+ batch `resolveJobsBySlug`, + `resolveJobInteractionFromJobSlug`) live in [resolve.ts](src/server/entities/resolveBySlug.ts). They accept slug OR cuid (slug first, id fallback) so replayed ids still resolve — keep the fallback.
2. **Outputs the agent reads emit the slug** — quote `r.value.slug`, never `${companyId}`.
3. **Mint a slug at every CREATE site** with `mint{Job,Opportunity,Contact}Slug` (one file per entity folder, over the shared [`mintSlug`](src/server/platform/slug/mintSlug.ts) core) — race-safe (retry-on-P2002), so run them **outside** any enclosing `$transaction`. `Company.slug` is minted at company-stub creation (`createCompanyStubs`, shared by `create_companies` + the `find_companies` checklist add).
4. **Stays a cuid** (don't "fix"): widget payload fields, the `focus` UiEvent contract, `ChatSession.focused*Id` slots, bundled-action signatures, and sub-agent I/O. (Memory paths are now slug-addressed — `jobs/{slug}.md` / `opportunities/{slug}.md` — the store's `resolveFK` accepts slug-or-cuid.) JobInteraction ids are never LLM-facing (agent uses the job slug; server resolves `(userId, jobId)`).

## Adding a new JobInteractionStatus / CompanyStatus value

A status enum addition touches ~12 surfaces in lockstep; miss one and the symptom is silent (wrong color/bucket, never surfaces in `runWhatsNext`) — not a typecheck error. In order:

1. **`prisma/schema.prisma`** — the enum value + any per-row reason/note/date columns on `JobInteraction`/`CompanyInteraction` + the matching reason-enum type if it carries structured "why."
2. **Migration file** — `ALTER TYPE … ADD VALUE` + any `ALTER TABLE` by hand. Don't apply from a worktree without the maintainer.
3. **`pnpm db:generate`** — else the value is invisible to the typechecker (your tsc safety net).
4. **[statusColors.ts](src/lib/statusColors.ts)** — add to a tone `case` in `statusTone()` (new tone → extend `StatusTone` + `theme.ts`). Add a `STATUS_LABELS` entry if the name shouldn't render verbatim.
5. **[hank/system.ts](src/server/agent/hank/system.ts)** — three sites: (a) the preamble's `# Translate, don't parrot` list (global); (b) the relevant per-mode body describing the semantics (walkthrough body owns lifecycle); (c) any flow step / tool description mentioning the prior status set.
6. **Job status: [logJobEvents.ts](src/server/agent/tools/registry/logJobEvents.ts) / [closeJob.ts](src/server/agent/tools/registry/closeJob.ts) / [deferJob.ts](src/server/agent/tools/registry/deferJob.ts); company status: the four per-status tools [closeCompany.ts](src/server/agent/tools/registry/closeCompany.ts) / [pauseCompany.ts](src/server/agent/tools/registry/pauseCompany.ts) / [blockCompany.ts](src/server/agent/tools/registry/blockCompany.ts) / [caughtUpCompany.ts](src/server/agent/tools/registry/caughtUpCompany.ts)** (the single `update_company_status` tool is gone) — the granular status writers: add reason/note validation + the clear-on-transition rule (next section).
7. **The set-aside writes** — [companies/setCompanyAside.ts](src/server/entities/companies/setCompanyAside.ts) (`closeCompany` / `blockCompany` / `pauseCompany` / `caughtUpCompany`), [companies/resumeCompany.ts](src/server/entities/companies/resumeCompany.ts) (`switchToCompany` / `reviveCompany`), [jobs/setJobAside.ts](src/server/entities/jobs/setJobAside.ts) (`closeJob` / `deferJob` / `promoteJobForWork`), [jobs/markJobApplied.ts](src/server/entities/jobs/markJobApplied.ts). If the status is reachable through one of these, handle it in that transaction; mirror clear-on-transition. Add the user-facing wording in [walkthrough/narration.ts](src/server/procedures/registry/walkthrough/narration.ts), never in the write.
8. **Gates** — the caught-up open-roles check in [caughtUpCompany.ts](src/server/agent/tools/registry/caughtUpCompany.ts): `SHORTLISTED`/`SCANNED` roles make the first call bail to a confirmation instead of setting the status (Hank re-calls with `confirmed: true`). Decide whether the new status counts as open work there. (This replaced the old hard `CAUGHT_UP_BLOCKING_STATUSES` gate in `tools/lib/watchlist.ts`, which erred instead of asking; both that file and `update_company_status` are deleted. The older between-companies compaction gate in `setFocus.ts` is gone too — focus is ephemeral, and the wrap that compacts runs from `runUserMessage`, not a gate.)

## Reason-carrying status pattern (`CLOSED`, `PAUSED`, `BLOCKED`)

Three company statuses carry a structured _why_: `CLOSED` (`closeReason` + `closeNote`), `PAUSED` (`pauseReason` + `pauseNote`), `BLOCKED` (`blockReason` + `blockNote`). (Company `PAUSED` is the former `DEFERRED`; the `deferredUntil` revisit timer was removed — paused companies never auto-resurface. Company `ACTIVE` is now `APPLYING`, plus two **auto-derived** engagement statuses `IN_FLIGHT` / `IN_PROCESS` computed in [engagement.ts](src/server/entities/companies/engagement.ts). Job `DEFERRED` kept its name, reframed as "could apply, outranked for now"; the shortlist defer-the-rest stamps `OUTRANKED`.) Load-bearing pieces:

- **Required enum + optional freeform note.** The structured reason is what the dashboard, sub-agents, and `whats_next` query against; the note captures what the enum can't. Tool validation rejects the status without its reason.
- **Symmetric field rejection.** Passing `closeReason` with status≠CLOSED (etc.) errors out — the mispairing signals agent confusion; silently stripping would hide it.
- **Clear-on-transition.** Every company `*_status` write sets ALL reason/note fields explicitly (the matching status's, plus `null` for every other status's) so a status chain never strands an old `closeReason` / `blockReason`. **The single enforcement point is [`companyStatusFields()`](src/server/entities/companies/companyStatusFields.ts)** — a discriminated union that makes "set a reason without its matching status" a compile error, so the rule can't be hand-rolled wrong. Funnel every company-status update through it; its callers are [setCompanyAside.ts](src/server/entities/companies/setCompanyAside.ts) + [resumeCompany.ts](src/server/entities/companies/resumeCompany.ts), [markCompanyStatus.ts](src/server/entities/companies/markCompanyStatus.ts) (`markCompanyReady` / `markCompanyCaughtUp` / `markCompanyPostFilter` — the add + re-scrape seams; PRE_SCAN itself writes no company status), [updateCompanyInteraction.ts](src/server/entities/companies/updateCompanyInteraction.ts), [enrichCompanies/statusWrites.ts](src/server/procedures/registry/enrichCompanies/statusWrites.ts), and [dispatchNextCompanyPicker.ts](src/server/widgets/dispatchNextCompanyPicker.ts). A fourth reason-carrying status adds a variant to that union and nothing else. (It replaced ~11 hand-written copies of the nulling.)

`JobDeferReason` and `CompanyPauseReason` are deliberately separate enums (different decision shapes per level), and both carry `OTHER` — so a sibling-enum value is the obvious agent slip. Each reason param is a strict `z.enum` over its **own** offered list — `JOB_DEFER_REASONS` from [entities/jobs/jobInteractionInputs.ts](src/server/entities/jobs/jobInteractionInputs.ts) on `defer_job`, `COMPANY_PAUSE_REASONS` from [entities/companies/companyInteractionInputs.ts](src/server/entities/companies/companyInteractionInputs.ts) on `pause_company` — and the same list is what the JSON schema shows the model. What removed the foot-gun was **splitting the tools**: there is no longer one `update_jobs_status` / `update_company_status` pair taking a dynamic status plus whichever reason matched, so a job reason and a company reason are never parameters of the same call. The old cross-enum `validateDeferReason()` hint (and `tools/lib/deferReasons.ts`) is deleted with them; don't reintroduce a shared reason param that needs it.

# LLM providers, keys & runtime

## LLM provider selection: DeepSeek sole, Anthropic vision-only

Full architecture in [docs/llm-providers.md](docs/llm-providers.md). DeepSeek runs the main chat agent AND every sub-agent; Anthropic survives only for vision. **There is no provider selection** — no per-user toggle, no env override, no capability flag. The gotchas:

- **`resolveLlmClient(userId, { model })` is the single entry — never `new Anthropic(...)` at a call site** (only legit exception: the key-validation test call in [settings/actions.ts](src/app/settings/actions.ts)). It answers exactly one question — which key pays for the model you named — and returns `{ client, model, billedToServer }`; pass that `model` to BOTH `messages.create/stream` AND `recordUsage`. Provider comes from the [`MODELS`](src/server/platform/llm/models.ts) table (`deepseek-v4-*` → DeepSeek, `claude-*` → Anthropic), and `LlmModel` is a closed union so a typo'd id is a compile error.
- **Vision runs on Anthropic because it names a Claude model, not because anything routes it there.** DeepSeek rejects image/document blocks, so the resume parser and logo verifier declare `claude-*`. Those two features need an Anthropic credential (own or server); both degrade gracefully if absent — don't "fix" by moving them to a DeepSeek model, the request 400s.
- **One flag gates both server keys.** `canUseServerKey` (per-user boolean, default false) controls the server fallback for `DEEPSEEK_API_KEY` AND `ANTHROPIC_API_KEY` — no separate per-provider flag. A user's own key always wins over the server key. Renamed from the legacy `canUseServerAnthropicKey` (column + field, migration `20260720120000_rename_can_use_server_key`); the `/admin/users` toggle writes it.
- **The per-user provider toggle is gone** — the `User.preferredLlmProvider` column was dropped (same migration as the `canUseServerKey` rename). Provider is env/default only.
- **The model lives with the sub-agent, and nothing may substitute it.** Each call site declares one `const MODEL: LlmModel = "deepseek-v4-flash"` next to its prompt (`HANK_MODEL` for the main agent), carrying its audit history as a comment; that model is what runs. Don't change a pin without re-auditing, and **don't reintroduce anything that remaps a declared model** — not an operation→model lookup (platform code must not enumerate domain operations; `resolveLlmClient` takes no `operation`), not a per-provider `{ deepseek, anthropic }` fork, not an env tier override. All three existed and were removed for the same reason: the model a call site names has to be the model that runs, or every audit result is about a different model than prod. DeepSeek requests are normalized in [platform/llm/deepseek.ts](src/server/platform/llm/deepseek.ts) (thinking disabled by default unless the call site sets it, so forced-schema sub-agents stay disabled but the main agent opts in explicitly; `max_tokens` doubled; `cache_control` a no-op) — wrap any new SDK entry point there too.

## LLM API keys (DeepSeek for chat, Anthropic for vision)

Symmetric key paths: `resolveDeepseekApiKey` + `deepseekKeyEncrypted`/`deepseekKeyHint` (primary — chat) and `resolveAnthropicApiKey` + `anthropicKeyEncrypted`/`anthropicKeyHint` (vision only).

- **Never read `process.env.DEEPSEEK_API_KEY` / `ANTHROPIC_API_KEY` directly** — go through `resolveDeepseekApiKey(userId)` / [`resolveAnthropicApiKey(userId)`](src/server/platform/llm/resolveAnthropicKey.ts). Each returns the user's decrypted key, falls back to the server key only when `canUseServerKey`, else throws `NoDeepseekKeyError` / `NoAnthropicKeyError`. A new sub-agent takes `userId`, calls the resolver at the top, returns its existing error shape on catch.
- **Keys are AES-256-GCM encrypted at rest** under `ANTHROPIC_KEY_ENCRYPTION_KEY` (base64, 32 bytes). Crypto boundary: [keyCrypto.ts](src/server/platform/llm/keyCrypto.ts) — provider-neutral, encrypts both keys (single swap point for KMS). **Never log the decrypted key.** `*KeyHint` stores the last 4 chars plaintext for UI confirmation.
  - **`encrypt`/`decryptApiKey` take a `KeyBinding` (`{ userId, provider }`) that becomes the GCM AAD**, so a ciphertext authenticates in exactly one (user, provider) cell — a blob copied into another user's row fails to decrypt instead of silently billing the wrong account. A third provider passes its own binding; don't add an unbound overload. Ciphertext is **version-tagged**: `v1.` + base64(iv‖tag‖ct). The tag is a string prefix, not a byte in the envelope, because `.` isn't in the base64 alphabet — a leading version byte is indistinguishable from a random IV byte 1 time in 256, and the prefix makes a format audit a plain predicate (`NOT LIKE 'v1.%'` must return 0 rows). Re-run [scripts/regression/key-crypto.ts](scripts/regression/key-crypto.ts) (no DB, throwaway master key) after any change here.
  - **Changing the key format = convert every row with a one-shot script in [scripts/migrations/](scripts/migrations/README.md), THEN ship the reader — `keyCrypto.ts` never carries a compatibility branch.** A dual-format reader is permanent by default: nothing fails once the data is converted, so nobody deletes it. So the old reader is reproduced *inside* the migration script (its only copy) and dies with `git rm` when the script reports 0 remaining. The ordering has an unavoidable window (old code can't read new blobs and vice versa), so run the two steps back-to-back and check the blast radius first: a user mid-window resolves no own-key and falls back to the server key if `canUseServerKey`, else the feature errors.
- **The chat client gates on one signal: `apiKeyBlocker` in [chatStore](src/lib/chatStore.ts).** Six SSE codes set it, three per provider — DeepSeek (primary, chat): `NO_DEEPSEEK_KEY` (pre-flight in `runUserMessage`), `INVALID_DEEPSEEK_KEY` (401 mid-turn), `DEEPSEEK_NO_CREDIT` (402 / `/balance|insufficient/i`); Anthropic (vision / override): `NO_ANTHROPIC_KEY`, `INVALID_ANTHROPIC_KEY`, `ANTHROPIC_NO_CREDIT`. The mid-turn pair is classified by `classifyLlmError` in [chat/route.ts](src/app/api/chat/route.ts) — a bare `Anthropic.APIError` reaching the chat catch is a DeepSeek error (the main agent is DeepSeek; vision faults never propagate there), so it emits the DeepSeek codes. [`ApiKeyBlockerModal`](src/components/ApiKeyBlockerModal.tsx) is paste-fixable for BOTH providers (`isDeepseek` picks `saveDeepseekKey` vs `saveApiKey`); the composer derives `canChat = apiKeyBlocker === null` so an in-modal save unblocks on the same tick. Don't add a parallel "chat gated" signal — extend the blocker reasons. `TopBar` sits at `z-index:1001` above the `1000` backdrop so Sign out / Settings stay reachable.
- **The balance regexes are fragile.** Neither shortage carries a typed code — DeepSeek's 402/400 matches `/balance|insufficient/i`, Anthropic's 400 matches `/credit balance/i`; a re-word silently degrades to the generic path. Same matches in `validateDeepseekKey` / `validateAnthropicKey` ([settings/actions.ts](src/app/settings/actions.ts)) — re-grep both if detection stops.
- **Mid-turn key errors classify only at the chat route's outer catch** (via `runUserMessage`). Only the main-agent (DeepSeek) stream fault propagates there; vision Anthropic faults are swallowed / converted to `is_error` tool_results and never reach it. New surfaces calling either provider outside `/api/chat` (other routes, server actions, scripts) need their own `APIError` classification — the modal isn't a global interceptor.

## Chat streaming resilience

- **A thrown error emits a terminal `done` after the `error` event.** The chat route's outer catch enqueues both before closing, so a still-connected client reconciles against the DB (pipelines persist each turn's progress as `ChatMessage` rows + flush partials on throw).
- **The `stoppedByUser` flag / "interrupted" pill / resume note cover THREE cut-off causes, not just Stop.** A user Stop abort, a transient server↔Anthropic socket drop, AND a genuine mid-stream fault (API 4xx/5xx that isn't a socket drop) all persist the partial that streamed with `stoppedByUser=true` so it's resumable. [`runAgentTurn`](src/server/agent/runtime/runAgentTurn.ts) distinguishes them: Stop/socket-drop → `stopped:true` (clean end); a genuine fault → `errored:<err>` (still returns the partial, but the runner persists it THEN re-throws so the error surfaces via the key-modal classification). Because the one flag covers all three, the pill ("Response interrupted") and the `STOPPED_REPLY_RESUME_NOTE` are deliberately cause-neutral — the column name `stoppedByUser` is now a slight misnomer (kept to avoid a migration).
- **Reconcile-on-return is the real fix for a missed terminal event.** A backgrounded tab isn't reading the stream when `done`/`error` arrives, so [`ChatHydrator`](src/components/ChatHydrator.tsx) reconciles on `visibilitychange`/`pageshow`/`online` via `reconcileFromServer()` ([chatStore.ts](src/lib/chatStore.ts)) — self-guarded against firing mid-stream (would clobber the optimistic message). The DB is the source of truth.
- **The server no longer aborts on client disconnect.** A disconnect only flags the client gone; the chat route keeps DRAINING `runUserMessage` to completion (bounded by `MAX_RUN_MS`, 5 min) so a long revive/scan finishes + persists. An intentional **Stop** aborts through a single bodyless `POST /api/chat/stop`, NOT the SSE fetch-abort. A `: keepalive` SSE comment every 15s prevents idle-timeout during long silent server phases.
- **The `MAX_RUN_MS` cap must TERMINATE the stream, not just abort the run.** The 15s keepalive is double-edged: it also stops the client's no-bytes watchdog from ever firing, so a WEDGED run (a hung DB call, a loop that never checks the abort signal) that never yields another event would keep the heartbeat alive and trap the client in `streaming` forever with a dead Stop button — the exact "spinner hung, only a refresh fixed it" bug. So at the cap the chat route emits a terminal `error`+`done` and closes the stream (via a guarded `closeStream()`), in addition to `runController.abort()`. A wedged run whose `finally` never runs also never calls `clearActiveRun`, so its registry entry lingers — [`claimSessionForNewRun`](src/server/agent/runtime/stopRegistry.ts) reclaims a stale run (controller already aborted, or older than `MAX_RUN_MS`) on the user's next message instead of refusing it with `ALREADY_STREAMING`, so "couldn't chat until a process restart" can't happen. It still refuses a genuinely-live run (the interleave guard).
- **Three client-side stuck-chat guards in [chatStore.ts](src/lib/chatStore.ts).** (1) `turnEpoch`: `refetchSession` discards a `/api/session` response fetched before a newer turn (or `newChat`) started — without it, the end-of-turn refetch racing a queued/fast send replaced `messages` with a pre-send snapshot, wiping the new optimistic user+assistant pair; the live stream then routed every event to a message id no longer in the array, so the chat "rolled back" and froze with the thinking shimmer stuck on. (2) A 45s no-bytes watchdog in `readSSE` (server keepalive is 15s): a half-open socket otherwise hangs `reader.read()` forever with `streaming: true`, which the reconcile guard (previous bullet) can never repair — only a refresh could. (3) A queued send bounced with `ALREADY_STREAMING` is handed to the drain poll (next bullet) instead of retried on a timer — a timed re-flush tight-loops refuse→requeue→resend against a run that can hold the session for minutes.
- **A draining run is visible: `runActive` + the drain poll.** `/api/session` reports `runActive` (from the in-memory [stopRegistry.ts](src/server/agent/runtime/stopRegistry.ts), same process as the `ALREADY_STREAMING` guard). When `refetchSession` sees `runActive: true` with no live local stream — dropped SSE, refresh mid-run, `ALREADY_STREAMING` bounce — it sets `serverRunActive`, which renders the "Hank is still working…" notice (ChatPanel) and arms a 3s poll loop; each tick repaints newly persisted progress, and the tick that sees the flip to false runs the end-of-turn refresh + flushes the queued send. Poll gives up after ~6 min (server run cap is 5). Without this the client had no way to learn a drained run existed or finished: a mid-drain reconcile silently replaced the streamed processing UI with the partial persisted turn and the finished result never appeared until a manual refresh (the "it removed those UI elements with no indicator" bug).
- **Stop is single-press, immediate, and save-what-streamed.** One press POSTs `/api/chat/stop`, which aborts the run's `AbortController` ([stopRegistry.ts](src/server/agent/runtime/stopRegistry.ts)) — tearing down the in-flight Anthropic stream + the currently-running tool call at once (`ctx.signal`). The runner catches the abort, degrades to the partial that already streamed, persists it with `stoppedByUser=true`, and emits the terminal `stopped`+`done` (which the client keeps reading — no reconcile flash). There is **no soft/hard two-tier and no second-press escalation** (the old dead `softStop` flag + 5s timer are gone). But Stop must ALWAYS hand control back, even when the server can't help: `stop()` unsticks the UI immediately if the endpoint reports no active run (`{stopped:false}`) or errors, and otherwise arms a `STOP_TERMINAL_GRACE_MS` (~5s) fallback that aborts the local fetch — triggering the send() catch → reconcile — if the terminal never arrives (a wedged run). This is an internal safety net, not a user-facing second tier. Because Stop rips a tool mid-flight, every agent tool must be abort-safe (transactional / idempotent / resumable). Resume has no first-class widget: [`loadSessionMessages`](src/server/agent/session/) injects a model-facing `STOPPED_REPLY_RESUME_NOTE` into the user turn following a stopped reply so Hank can offer to pick up where it left off.

## Ending a company: the mutation writes, the runner wraps

`close_company` / `pause_company` / `block_company` / `caught_up_company` (one file each under [src/server/agent/tools/registry/](src/server/agent/tools/registry/)) only **set status**, via their [`setCompanyAside`](src/server/entities/companies/setCompanyAside.ts) function. Close also bulk-closes the company's open jobs; block touches no jobs, since "couldn't read the board" says nothing about a role.

The **segment wrap** — consolidate memory, compact the transcript, relay to Hank — is [`procedures/registry/wrapCompanySegment.ts`](src/server/procedures/registry/wrapCompanySegment.ts), and **`runUserMessage` is its only caller**. Bundled actions exist to make several related WRITES happen canonically in one call so a caller can't get half of them wrong; a two-sub-agent chain that truncates the chat transcript is not that, and compaction is a session concern a company mutation has no business knowing about. It also has to run **once per message**: since these tools aren't `handoff`, "close these three" is one turn with three calls, and the wrap living in the mutation meant three full consolidation passes (`runCompactSession` self-limits after the first; `runConsolidateSessionMemory` does not).

**Two different signals, do not merge them.** `endedCompanyId` (on `WalkthroughResult` / `ToolResult` → the `done` event) means *a company ended* → run the wrap. `wrappedUp` means *bring up what's next* — and half a dozen paths set it with no company having ended (revive declined, profile intake finished, a job-gone fallback, the no-target dispatch branch). Keying the wrap off `wrappedUp` would compact on all of them.

**None of these tools is `handoff: true`, and none should become one.** A handoff ENDS Hank's turn — right for an entry into a sequence, wrong for a mutation: it cuts his reply off mid-sentence and caps "pause these six" at one company (the reason there was no bulk company-status tool). Use a result field rather than the static `handoff` flag whenever *whether* something ended is an outcome — `caught_up_company` bails to a confirmation when open roles remain and ends nothing.

Earlier machinery here is **gone**; don't reintroduce it: the `wrap: false` param, `EntryTarget`'s `intent: "wrap"` discriminator, and the state machine's `TERMINAL_COMPANY_STATUSES` re-detection in `dispatchByEntryTarget`. All three existed to defer the wrap to the walkthrough state machine, which is now neither where it lives nor how it's triggered.

**`block_company` is for "I genuinely couldn't read their careers page," NOT a fit pass** — that's the exact bug BLOCKED exists to prevent.

# Observability, admin & platform

## Admin observation gotchas

AdminNotes are now written **only** by the two offline audit harnesses ([session-audit](scripts/audits/sessions/README.md) + [sub-agent runtime audit](scripts/audits/sub-agent-runs/README.md)) — the runtime self-diligence channels (the `record_observation` / `request_capability` tools, the universal sub-agent signal fields, the hand-rolled anomaly flaggers, the tool-side `expectations` blocks, and the client-error fan-out) were all removed. Runtime agents and sub-agents no longer file AdminNotes.

- **Never `prisma.adminNote.create()` directly — always [`upsertAdminNote()`](src/server/platform/admin/adminNotes.ts).** It match-or-inserts on `(userId, category, dedupKey, dismissed=false)`; inlining `create` breaks dedup and spams a row per turn. It also handles severity escalation, `lastSeenAt`, message-FK resolution, and dismiss-resets-chain. Its only callers are the two audit harnesses.
- **`dedupKey` is the audit harnesses' convention, not freeform.** Shape `<source>:<failure mode>:<input shape>` (e.g. `subagent_runtime:weird_output:<op>:<shape>`). Pick the key before writing the code and grep for collisions.

## Admin view-session impersonation: route convention

`/admin/session/[sessionId]` loads any user's ChatSession read-only via `?impersonate=<sessionId>`, routed through two helpers in [viewerScope.ts](src/server/auth/viewerScope.ts). Design: [docs/admin.md](docs/admin.md#view-any-users-session-adminsessionsessionid). The convention (the only safety net — no automated check):

- **Every new GET that scopes by `userId` uses `resolveViewedUser(req)`**, not `getCurrentUser()` — else it silently returns the admin's data in view-session mode.
- **Every new write/streaming route calls `rejectImpersonatedWrite(req)` at the top** and returns its Response if non-null — guards against a future UI bug posting under the wrong identity.
- Routes not scoping by userId (global lookups, health checks) need neither. `/api/admin/*` already goes through `requireAdmin()`; everything else under `/api/*` touching per-user data needs the helpers.

## Web Push gotchas

- **`notifyAdmin(title, body)` is the single choke point** — don't sprinkle `webpush.sendNotification`. Fire-and-forget + missing-env-noop already baked in; use it only for genuinely urgent admin signal.
- **Subscriptions live in the `PushSubscription` table, not env** — [`/admin/push-subscribe`](src/app/admin/push-subscribe/page.tsx) upserts by endpoint; adding/removing a device is a UI action. Failed 404/410 pushes auto-prune inside `notifyAdmin`.
- **Rotating VAPID keys invalidates every subscription** (the key is baked in at `subscribe()` time; the push service verifies the JWT against the bound key). Recovery: re-visit the subscribe page per device; the next push 4xxs and auto-prunes. VAPID env vars are read at startup — changing them needs a restart.
- **`/sw.js` and `/manifest.webmanifest` must stay in `PUBLIC_PATHS`** ([proxy.ts](proxy.ts)) — fetched with no auth context; add any future PWA static asset there too, or the browser 302s to `/signin` and silently disables PWA behavior.
- **iOS Web Push requires an installed PWA** — `Notification.requestPermission()` only resolves inside a home-screen PWA (Safari ≥16.4). The subscribe page detects `display-mode: standalone` and shows install instructions instead; mirror that check in any other permission flow.

## Mobile Safari + styled-components gotchas

- **iOS auto-zooms a focused form field with `font-size < 16px`.** [globals.css](src/app/globals.css) forces 16px on form fields under `max-width:900px`; **the `!important` is load-bearing** — a plain element selector (0,0,1) loses to the styled-component class (0,1,0). Don't strip it. (The `maximum-scale=1` alternative disables pinch-zoom — an accessibility regression we avoid.)
- **Apple touch icons want square PNG, not SVG** — iOS rasterizes SVGs poorly and applies its own rounded mask (pre-rounding leaves transparent corners). Provide `src/app/apple-icon.png` (180×180, no border-radius); same square shape for the manifest maskable PNGs. Add any new icon path to `PUBLIC_PATHS` in [proxy.ts](proxy.ts).

# Workflow

## Finish the refactor. Don't leave a tombstone.

**This is a prototype. Churn is cheap; a codebase nobody can hold in their head is not.** The failure mode this rule exists to stop: an agent asked for a sweeping change does the easy 70%, then protects the rest behind a `// legacy` comment, a "kept for old rows" enum value, an alias map, or a deprecated-but-still-exported function — and reports the refactor as done. Ten of those and every read costs double: two names per concept, two code paths per behavior, and docs describing a shape that no longer exists.

**"It would be a lot of work" and "I'm worried about breaking the experience" are not reasons to leave a half-migration behind.** They're reasons to write the migration down and do it. If the whole thing genuinely can't land in one pass, that's fine — but the remainder gets tracked, not silently absorbed.

**A refactor is DONE when all five are true:**

1. **No caller is left on the old path.** Every call site moved; the old function / column / enum value / tool / file is **deleted**, not left exported with a comment explaining that it's dead.
2. **The data is migrated.** A schema-shaped refactor is not complete until the backfill is written AND applied to prod (see "Prisma schema changes"). **A lazy "backfill it when the row is next touched" path is a migration you haven't run** — rows nothing touches stay wrong forever, and you can't ever delete the fallback that reads them. Write the one-shot backfill, run it, then delete the lazy path. `Job.slug` is the cautionary tale: 57% of rows never got one.
3. **The names tell the truth.** Renamed concept → rename it everywhere: filename, export, type, param, schema field, DB column, prompt text, doc prose. One name per concept (see Conventions).
4. **The docs match the code.** `AGENTS.md` + `docs/` are load-bearing context, not commentary — a doc pointing at a deleted file actively misleads the next agent, on every future task. **A moved file silently breaks every markdown link to it**, so after any rename or move, re-grep the docs for the old path AND the old symbol name and fix every hit (there's a link-check one-liner at the bottom of [docs/INCOMPLETE_MIGRATIONS.md](docs/INCOMPLETE_MIGRATIONS.md)).
5. **Nothing is marked "legacy" that isn't.** Before writing `// legacy` / `// deprecated` / `// kept for old rows`, **run the count** — `select count(*) … where x = 'OLD_VALUE'`. Most of the time it's zero and the tombstone is imaginary. 21 of this repo's enum tombstones have never had a single backing row, and four of them cost tokens on every turn because a tool description tells the model not to emit them.

### If you genuinely must leave something behind

Sometimes the compat path is real — persisted chat history you can't rewrite, a prod secret whose name is baked into a deploy. Then:

- **File it in [docs/INCOMPLETE_MIGRATIONS.md](docs/INCOMPLETE_MIGRATIONS.md)** — the single index of every unfinished migration and compat shim. An entry names the old shape, why it survives, what still depends on it (row counts, not guesses), and the exact steps left. **No entry = no shim.** Delete the entry when the migration lands; don't edit it to say "done".
- **Say it in the response, up front.** Name what you did NOT finish, in plain words, at the top — never buried at the end or left implied. "Refactor done; one compat path left for persisted history, filed in INCOMPLETE_MIGRATIONS.md" is a fine report. "Done." while a shim survives is not.
- **Prefer deleting to deprecating.** In a fast-moving prototype, a wrong delete is a `git revert`. A tombstone is forever, because the next agent won't know whether it's load-bearing either.

**When a change is big enough to need staging, write the migration plan first** — end state, every call site, the backfill, the doc updates — and hand it to the maintainer before starting, rather than discovering halfway through that it's "a lot of work" and quietly narrowing scope.

## Don't commit without being asked

Stage and write changes freely, but **don't `git commit` until the maintainer asks** — they review the diff first, and agent-written messages run long against their terse style (that context belongs in the PR/doc). Same for `git push`. Exception: if the maintainer says "commit this" / "push this" or sets up a checkpointed workflow. Default: leave it staged, surface what changed in the response.
